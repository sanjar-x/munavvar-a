## 1. Назначение документа

Настоящий BRD определяет бизнес-требования к Dashboard API — набору серверных эндпоинтов, которые обеспечат все экраны дашбордов админ-панели MunavvarA агрегированными данными. Dashboard API не затрагивает UI — он обслуживает фронтенд-компоненты, описанные в UX/UI-исследованиях.

---

## 2. Бизнес-контекст

### 2.1 Проблема

Текущая система MunavvarA имеет MVP-набор CRUD-эндпоинтов и один базовый финансовый дашборд (`GET /finances/dashboard`), который возвращает моментальный снимок: total_revenue, total_cash_in_hand, total_card_pending, total_client_debt, total_courier_cash, pending_transactions_count (dashboard_finance.md §2.2). Однако для полноценной работы 5 штатных ролей (Администратор, Бухгалтер, Кладовщик, Кассир, Курьер) необходим **аналитический** слой данных — временные ряды, aging-бакеты, агрегаты по сегментам, что существующий endpoint не покрывает:

- **Администратор** не видит сводку дня (заказы по статусам, незакрытые смены, курьеры на линии)
- **Бухгалтер** не имеет aging-анализа дебиторки, динамики выручки, статистики подтверждений
- **Кладовщик** не видит распределение тары, тренды остатков, алерты по критическому запасу
- **Администратор-диспетчер** не может на одном экране увидеть загрузку курьеров и незназначенные заказы

### 2.2 Бизнес-цели

| #    | Цель                                                 | Метрика успеха                                     |
| ---- | ---------------------------------------------------- | -------------------------------------------------- |
| BG-1 | Сократить время принятия оперативных решений         | Диспетчер назначает курьера за < 30 сек            |
| BG-2 | Обеспечить бухгалтеру полную финансовую прозрачность | Подтверждение карточного платежа за < 10 сек       |
| BG-3 | Минимизировать потери тары                           | Процент возврата тары > 95% (виден на дашборде)    |
| BG-4 | Предотвратить складские дефициты                     | Алерты о низком остатке видны в реальном времени   |
| BG-5 | Обеспечить аналитику для стратегических решений      | Доступ к трендам выручки, заказов, оборачиваемости |

### 2.3 Заинтересованные стороны

| Роль                      | Интерес                                                   |
| ------------------------- | --------------------------------------------------------- |
| CEO/Директор              | Стратегические KPI: выручка, рост, эффективность          |

## 3. Scope (Объём)

### 3.1 В объёме (In Scope)

Dashboard API охватывает **четыре домена** данных:

1. **Операционный дашборд (Orders & Dispatch)**
   - Счётчики заказов по статусам (real-time)
   - Сводка загрузки курьеров
   - Тренды объёма заказов по дням/неделям/месяцам
   - Воронка конверсии статусов заказов
   - Тепловая карта пиковых часов заказов
   - Распределение способов оплаты
   - Метрики частичных доставок
   - Топ-клиенты по объёму заказов
   - Разбивка B2B/B2C и Доставка/Самовывоз

2. **Финансовый дашборд (Finance)**
   - Динамика выручки по дням/неделям/месяцам с % изменения vs предыдущий период (BR-6)
   - Aging-бакеты дебиторской задолженности, адаптированные под недельный цикл (BR-7)
   - Разбивка по способам оплаты: `cash` / `card` / `contract` — суммы и количество (BR-5)
   - Топ-N должников по сумме с разделением источников долга (BR-8)
   - Расчётные KPI: средний чек, коэффициент инкассации, % просроченной задолженности (BR-9). DSO — отложен
   - Статистика подтверждения карточных платежей: среднее время, rejection rate (BR-9)
   - Выручка по сегментам B2B vs B2C (BR-20)

3. **Складской дашборд (Inventory)**
   - Агрегированная сводка: общий остаток воды, тары, оборудования, товар на курьерах, потери (BR-10)
   - Распределение тары: склады, курьеры, клиенты, потери — с разбивкой по типам бутылей (BR-11)
   - Должники по таре (топ-N клиентов с наибольшим объёмом невозвращённой тары) (BR-12)
   - Статистика перемещений по типам за период (BR-13)
   - Тренды остатков за 7/30 дней (BR-17)
   - Баланс виртуальных счетов (VIRTUAL_VENDOR, VIRTUAL_LOSS) + контроль целостности леджера (BR-18)

4. **Дашборд курьеров (Courier Fleet)**
   - Карточки курьеров: статус, остатки в машине, прогресс доставок, наличные, собранная тара (BR-14)
   - Загрузка курьеров по дням за период (BR-19)

### 3.2 Вне объёма (Out of Scope)

- Карта реального времени с GPS-трекингом курьеров
- Оптимизация маршрутов (route optimization)
- Предиктивная аналитика и прогнозирование спроса
- RFM-анализ клиентов
- Sankey-диаграмма денежных потоков (требует сложной агрегации, отложена)
- Sankey-диаграмма потоков товара между складскими точками (dashboard_inventory.md §3.3 — отложена)
- Экспорт отчётов в PDF/Excel (отдельный scope)
- Push-уведомления и WebSocket (отдельный scope)
- Мобильные дашборды курьера и клиента (у них свои эндпоинты)
- Система пороговых алертов (dashboard_inventory.md §9 — требует настраиваемых порогов, отдельный scope)
- Панель закрытия смены (dashboard_inventory.md §7.4 — это workflow, не dashboard; реализуется отдельно)
- Рейтинг курьеров по on-time % и среднему времени доставки (dashboard_orders.md §2.3 — требует `order_status_history`)
- UI-фреймворк, дизайн-система, компоненты, цветовая палитра (см. dashboard_ui.md — Ant Design v6 + Recharts)
- UX-workflow-ы: command palette, drag-and-drop диспетчеризация, клавиатурные сокращения, wizard закрытия смены, wizard онбординга клиента (см. dashboard_ux.md §4, §9)

## 4. Бизнес-требования

### 4.1 Глобальные правила фильтрации данных

Следующие правила применяются ко **всем** dashboard-эндпоинтам:

**Исключение системных пользователей:** Во всех запросах, возвращающих данные по клиентам, необходимо исключать:

- `SYSTEM_USER` — системный пользователь, не является реальным клиентом
- `WALKIN_USER` — анонимный покупатель, баланс обнуляется после каждой продажи (BUSINESS.md §4)

Walk-in заказы **включаются** в общую статистику (BR-1, BR-2, BR-3, BR-4, BR-5 — это реальные продажи), но **исключаются** из:

- Топ клиентов (BR-16)
- Должников по финансам (BR-8)
- Должников по таре (BR-12)

**Часовой пояс:** Все временные агрегации (heatmap, тренды за «сегодня») выполняются в `Asia/Tashkent` (UTC+5) — единственный рынок системы.

**Суммы:** Все денежные суммы возвращаются в тийинах (BIGINT). Конвертация в сумы — на фронтенде.

**Инверсия выручки (BUSINESS.md §8.1, dashboard_finance.md §11.2):** Баланс счёта `REVENUE` в системе всегда **отрицательный** (деньги «уходят» из выручки к клиентам). На дашборде выручка должна показываться как **положительное число** (`total_revenue = -revenue_balance`). Аналогично: долг клиента (положительный баланс на CLIENT-счёте) показывается как «задолженность», касса курьера — как «наличные на руках». Принцип: **скрыть механику двойной записи, показать бизнес-результат.**

### BR-1: Операционная сводка дня

**Описание:** Система должна предоставлять агрегированный снимок для администратора-диспетчера, разделённый на два блока: (а) текущие активные заказы (все даты) и (б) статистика за сегодня.

> **Обоснование разделения (dashboard_orders.md §2.1):** Диспетчеру критично видеть ВСЕ незавершённые заказы, включая вчерашние — «Незакрытые заказы старше 24ч без доставки» имеют целевое значение 0.

**Данные — Активные заказы (незавершённые, все даты):**

- Количество заказов в каждом из 4 незавершённых статусов: `new`, `assigned`, `in_transit`, `arrived`
- Количество незназначенных заказов (статус `new`, тип `delivery`, курьер не назначен) — ключевой показатель для диспетчера

**Данные — Статистика за сегодня:**

- Всего создано заказов сегодня
- Завершено сегодня (статус `delivered` + `pickup_completed`)
- Отменено сегодня (статус `cancelled`)
- Выручка за сегодня (сумма `total_amount` завершённых заказов), в тийинах
- Разбивка по типу продажи (`SaleType`): `delivery` / `warehouse_pickup`

**Данные — Ресурсы:**

- Количество активных курьеров (с активным транспортом, `inventories.type = 'COURIER' AND is_active = true`)

> **Примечание:** Показатель «количество незакрытых смен» отложен — требует дополнительной бизнес-логики определения «незакрытой смены» (нет явного поля `shift_closed` в модели).

**Составной паттерн «Требуют внимания» (dashboard_ux.md §2.2):** На домашнем экране администратора данные из BR-1 комбинируются с данными из других источников для формирования блока action-items:

- `unassigned_orders` (BR-1) → «N заказов без курьера»
- `pending_transactions_count` (существующий `GET /finances/dashboard`) → «N ожидающих подтверждения»
- Низкий остаток (BR-10, будущие алерты) → «Низкий остаток: Товар X на складе Y»

Это **фронтенд-композиция** — API предоставляет данные через отдельные эндпоинты, фронтенд собирает блок.

**Критерий приёмки:** Ответ формируется за < 500 мс. Данные актуальны с задержкой не более 60 секунд.

### BR-2: Тренд заказов по периодам

**Описание:** Система должна возвращать временной ряд количества и суммы заказов, группированный по дню/неделе/месяцу.

**Данные:**

- По каждому интервалу: дата, количество заказов, выручка, средний чек
- Фильтры: период (date_from, date_to), тип заказа (delivery/pickup/all), сегмент (B2B/B2C/all)

**Критерий приёмки:** Поддерживается диапазон до 365 дней. Ответ за < 1 сек.

### BR-3: Воронка статусов заказов

**Описание:** Распределение заказов по текущему статусу за период для визуализации конверсии.

**Данные:**

- Для каждого из 7 статусов (`OrderStatus`): сколько заказов за период **находится** в этом статусе
- Сортировка по порядку FSM: `new` → `assigned` → `in_transit` → `arrived` → `delivered` / `pickup_completed` / `cancelled`
- Процент от общего количества для каждого статуса
- Фильтр: период

> **Ограничение:** Это **распределение по текущему статусу**, а не истинная конверсионная воронка (для неё нужна таблица `order_status_history`, которой пока нет). Для бизнеса доставки воды распределение информативно: много в `new` → проблема назначения; много в `assigned` → курьеры не выезжают; высокий % `cancelled` → проблема качества.

**Критерий приёмки:** Данные за период до 90 дней за < 1 сек.

### BR-4: Тепловая карта заказов

**Описание:** Матрица (день недели × час дня) с количеством созданных заказов, для выявления пиковых часов.

**Данные:**

- 7 дней × 24 часа = до 168 ячеек
- День недели: 1=Пн..7=Вс (ISO 8601, `EXTRACT(ISODOW ...)`)
- Час дня: 0-23 по местному времени (`AT TIME ZONE 'Asia/Tashkent'`)
- Максимальное значение (`max_count`) для нормализации цвета на фронтенде
- Фильтр: период

**Критерий приёмки:** Данные за месяц за < 1 сек.

### BR-5: Разбивка способов оплаты

**Описание:** Распределение заказов и сумм по способам оплаты за период.

**Данные:**

- По каждому способу оплаты (`PaymentMethod` enum: `cash`, `card`, `contract`): количество заказов, общая сумма (тийины)
- Учитываются только завершённые заказы (статус `delivered` / `pickup_completed`)
- Фильтр: период

> **Бизнес-контекст (BUSINESS.md §6.3):** Самовывоз (`warehouse_pickup`) всегда оплачивается наличными. Поэтому `contract` будет содержать только delivery-заказы от B2B-клиентов.

**Критерий приёмки:** Ответ за < 500 мс.

### BR-6: Динамика выручки (временной ряд)

**Описание:** Система должна возвращать ряд точек (date, revenue_amount) для построения линейного графика.

**Данные:**

- По каждому дню/неделе/месяцу: сумма `total_amount` завершённых заказов (`delivered` / `pickup_completed`), количество заказов
- Итоги за весь период: `total_revenue`, `total_orders`
- **Процент изменения** vs аналогичный предыдущий период (dashboard_finance.md §5.3: «трендовые стрелки — рост/падение по сравнению с предыдущим периодом»). Например: если запрошена неделя 24-30 марта, сравнить с 17-23 марта.
- Фильтр: период, гранулярность (day/week/month)

> **Источник данных:** Таблица `orders` (не `transactions`). Для бизнес-аналитики выручки orders — первичный источник. Таблица transactions включает ручные проводки, инкассации и возвраты, не связанные напрямую с продажами, что исказит график.

**Критерий приёмки:** До 365 точек, ответ за < 1 сек.

### BR-7: Aging-бакеты дебиторской задолженности

**Описание:** Группировка клиентов-должников по давности долга.

**Три источника дебиторской задолженности (dashboard_finance.md §8.1, BUSINESS.md §8.2):**

1. **Карточные платежи до подтверждения** — клиент оплатил картой, транзакция в `PENDING`, балансы ещё не обновлены. Формально клиент числится должником до подтверждения бухгалтером.
2. **B2B-клиенты по договору** (`contract`) — долг накапливается сознательно, оплата по условиям контракта.
3. **Неоплаченные доставки** — редкая ситуация, когда доставка завершена, но оплата не прошла.

> **Правило обработки PENDING-должников:** Клиенты с PENDING карточным платежом **включаются** в aging-бакеты (они формально в долгу), но должны быть **визуально выделены** на фронтенде. API возвращает общие бакеты; фронтенд может запросить список должников (BR-8) и сопоставить с PENDING-транзакциями для визуального разделения.

**Бакеты** (адаптированные под недельный цикл заказов воды — dashboard_finance.md §8.2):

| Бакет          | Диапазон   | Интерпретация          |
| -------------- | ---------- | ---------------------- |
| Текущий        | 0–7 дней   | Нормальный цикл оплаты |
| Предупреждение | 8–14 дней  | Пропущен один цикл     |
| Просрочка      | 15–30 дней | Активная проблема      |
| Критично       | 31–60 дней | Требует вмешательства  |
| Безнадёжный    | 60+ дней   | Потенциальное списание |

> **Обоснование (dashboard_finance.md §8.2):** Стандартные 30-дневные бакеты (QuickBooks, Zoho) слишком грубые для бизнеса с недельным циклом заказов. Клиент, не плативший 14 дней, — уже проблема.

**Данные на бакет:** количество клиентов, общая сумма долга (тийины). Итоги: total_debt, total_debtors.

**Критерий приёмки:** Ответ за < 1 сек.

### BR-8: Топ должников

**Описание:** Список N клиентов с наибольшей задолженностью.

**Данные:** client_id, имя, тип (`client_b2c` / `client_b2b`), телефон, сумма долга (тийины), дата последнего платежа, дней без оплаты.

**Правила:**

- **Исключаются** системные пользователи (`SYSTEM_USER`, `WALKIN_USER`) — см. раздел 4.1
- «Дней без оплаты» = количество дней с момента последнего COMPLETED платежа клиента. Если клиент никогда не платил — от даты создания аккаунта

**Критерий приёмки:** Сортировка по сумме. Параметр limit (по умолчанию 10).

### BR-9: Расчётные финансовые KPI

**Описание:** Ключевые расчётные метрики за период.

**Данные:**

- **Средний чек (AOV):** выручка / количество завершённых заказов (тийины)
- **Количество заказов** за период (завершённых)
- **Общая выручка** за период (тийины)
- **Коэффициент подтверждения карточных платежей:** confirmed / total (из `transactions` с `to_id` → `accounts.type = 'CARD'`)
- **Коэффициент отклонения карточных платежей:** rejected / total
- **Среднее время подтверждения** карточных платежей (часы, `AVG(updated_at - created_at)` для COMPLETED)
- **Коэффициент инкассации:** (сдано курьерами / собрано курьерами) за период (dashboard_finance.md §3.2)
- **Процент просроченной задолженности:** (сумма долгов с давностью > 7 дней / общая сумма долгов) \* 100% (dashboard_finance.md §3.2). Порог «просрочки» = 7 дней, адаптирован под недельный цикл заказов воды.

> **DSO (Days Sales Outstanding)** — отложен. Требует сложной агрегации и чёткого определения «момента возникновения долга» vs «момента оплаты». Будет добавлен в следующей версии BRD.

**Критерий приёмки:** Ответ за < 1 сек.

### BR-10: Складская сводка

**Описание:** Агрегированные KPI по складскому учёту — моментальный снимок текущего состояния всех запасов.

**Данные:**

- Общий остаток воды (`products.type = 'water'`) на складах + курьерах
- Общий остаток тары (`products.type = 'container'`) на складах + курьерах
- Общий остаток оборудования (`products.type = 'equipment'`) на складах + курьерах
- Тара у клиентов (`inventories.type = 'CLIENT'`)
- Товар на курьерах — всего единиц (`inventories.type = 'COURIER'`)
- Потери за сегодня — сумма единиц в перемещениях типа `LOSS_WRITE_OFF` за текущий день
- Потери за период (параметр `date_from`/`date_to`) — для аналитики коэффициента потерь (dashboard_inventory.md §2.2: целевой < 1%)
- Количество активных курьеров на линии (с активным транспортом)

> **Тип продукта:** Различение воды, тары и оборудования выполняется через `ProductType` enum (`water` / `container` / `equipment`). BUSINESS.md §2 описывает три категории товаров: бутилированная вода, возвратная тара и оборудование (механические помпы и т.п.).

**Изоляция кладовщика:** При роли `STOREKEEPER` показываются только остатки на складах, где `owner_id = current_user.id`. Данные по курьерам и клиентам скрываются (BUSINESS.md §4: «Видит только свои склады»).

**Критерий приёмки:** Ответ за < 500 мс.

### BR-11: Распределение тары

**Описание:** Разбивка всей тары в системе по местоположению. Тара — ключевой актив бизнеса (~50 000 сум/шт, BUSINESS.md §2), и её распределение — центральный виджет складского дашборда (dashboard_inventory.md §3.5).

**Данные — Агрегат по всей таре (`products.type = 'container'`):**

- На складах (`WAREHOUSE`): количество
- На курьерах (`COURIER`): количество
- У клиентов (`CLIENT`): количество
- Потери (`VIRTUAL_LOSS`): количество
- Всего в системе (`|VIRTUAL_VENDOR|`): количество

**Данные — Разбивка по конкретным продуктам-тары:**

- Для каждого товара с `type = 'container'` (например, «Тара Hayot 19Л», «Тара MunavvarA 18.9Л»): количество по каждому типу инвентаря
- Это необходимо, так как BUSINESS.md §2 привязывает каждый вид воды к конкретному типу бутыли — нужно видеть баланс по каждому типу отдельно

**Критерий приёмки:** Ответ за < 500 мс.

### BR-12: Должники по таре

**Описание:** Клиенты с наибольшим объёмом невозвращённой тары.

**Данные:** client_id, имя, тип (`client_b2c` / `client_b2b`), количество тары на балансе (сумма `inventory_balances` где `products.type = 'container'` и `inventories.type = 'CLIENT'`), дата последнего завершённого заказа, дней с последнего заказа.

**Правила:**

- **Исключаются** системные пользователи (`SYSTEM_USER`, `WALKIN_USER`) — см. раздел 4.1
- Сортировка по количеству тары (убывание)

**Критерий приёмки:** Параметр limit (по умолчанию 10). Ответ за < 1 сек.

### BR-13: Статистика перемещений

**Описание:** Агрегация перемещений по типам за период.

**Данные:** Для каждого из 9 `TransferType` — количество перемещений и общий объём (единиц товара):

| #   | TransferType            | Описание                                             |
| --- | ----------------------- | ---------------------------------------------------- |
| 1   | `COURIER_LOAD`          | Загрузка курьера (Склад → Курьер)                    |
| 2   | `COURIER_RETURN`        | Возврат курьера (Курьер → Склад)                     |
| 3   | `CLIENT_DELIVERY`       | Доставка клиенту (Курьер → Клиент)                   |
| 4   | `CLIENT_RETURN`         | Возврат тары от клиента (Клиент → Курьер)            |
| 5   | `WAREHOUSE_SALE`        | Продажа со склада (Склад → Клиент)                   |
| 6   | `WAREHOUSE_TARA_RETURN` | Возврат тары на склад (Клиент → Склад)               |
| 7   | `LOSS_WRITE_OFF`        | Списание (→ VIRTUAL_LOSS)                            |
| 8   | `INVENTORY_FINDING`     | Находка (VIRTUAL_VENDOR →)                           |
| 9   | `INITIAL_BALANCE`       | Начальный остаток / капитализация (VIRTUAL_VENDOR →) |

Учитываются только завершённые перемещения (`TransferStatus.COMPLETED`).

**Изоляция кладовщика:** При роли `STOREKEEPER` показываются только перемещения, где склад-источник или склад-получатель принадлежит текущему пользователю (BUSINESS.md §13.14: «Кладовщик видит только свои склады и связанные с ними перемещения»).

**Критерий приёмки:** Фильтр: period. Ответ за < 500 мс.

### BR-14: Дашборд курьеров

**Описание:** Карточки всех активных курьеров с текущим состоянием.

**Данные на курьера:**

- ID, имя, номер машины (из `inventories.type = 'COURIER'`)
- Остатки товара в машине (по продуктам, из `inventory_balances`)
- Количество заказов: назначенных сегодня, доставленных сегодня
- Баланс наличных на руках (из `accounts.type = 'COURIER'`)
- Наличные, собранные за сегодня (сумма входящих `COMPLETED` транзакций на счёт курьера)
- Тара, собранная за сегодня (сумма `CLIENT_RETURN` перемещений за сегодня для container-продуктов) — dashboard_orders.md §6.5
- Статус: активен (есть транспорт) / не активен

**Агрегаты по всем курьерам:**

- Всего активных курьеров
- Всего товара на курьерах (единиц)
- Всего наличных у курьеров (тийины)

**Критерий приёмки:** Ответ за < 1 сек.

### BR-15: Метрики частичных доставок

**Описание:** Статистика частичных доставок за период.

**Данные:**

- Общее количество доставок
- Количество частичных доставок (где фактическое количество < заказанного)
- Процент частичных доставок

> **⚠ Ограничение:** Поле «потерянная выручка» (разница между заказанной и доставленной суммой) **невозможно вычислить** с текущей моделью данных. При частичной доставке `order_items.quantity` перезаписывается фактическим количеством, а `order.total_amount` пересчитывается. Оригинальные заказанные количества не сохраняются.
>
> **Зависимость:** Для корректной работы этого BR необходимо добавить поле `is_partial_delivery: bool` в модель `Order`, которое устанавливается при обнаружении частичной доставки в `_handle_order_fulfillment`. Без этого поля эндпоинт реализовать корректно невозможно.
>
> **Статус:** Отложен до реализации schema change (Фаза 3+).

**Критерий приёмки:** Фильтр: period. Ответ за < 1 сек.

### BR-16: Топ клиентов по заказам

**Описание:** Рейтинг N клиентов по количеству заказов и/или сумме за период.

**Данные:** client_id, имя, тип (`client_b2c` / `client_b2b`), количество завершённых заказов, общая сумма (тийины).

**Правила фильтрации:**

- Учитываются только завершённые заказы (`delivered` / `pickup_completed`)
- **Исключаются** системные пользователи (`SYSTEM_USER`, `WALKIN_USER`) — см. раздел 4.1

**Критерий приёмки:** Параметр limit (по умолчанию 10), сортировка по количеству или по сумме.

### BR-17: Тренды складских остатков

**Описание:** Временной ряд остатков ключевых категорий товаров за 7/30 дней для выявления трендов снижения запасов и планирования закупок (dashboard_inventory.md §3.2: Line Chart тренда остатков).

**Данные:**

- По каждому дню периода: суммарный остаток воды, тары на складах и тары у клиентов
- Источник: `stock_transactions` (append-only леджер), агрегация по дате создания
- Фильтры: период (date_from, date_to), категория товара (`ProductType`: water/container/all)

> **Бизнес-ценность (dashboard_inventory.md §2.2):** «Дни запаса (Days of Supply) = Текущий остаток / Средний дневной расход» — тренд позволяет видеть, когда запас приблизится к нулю. Целевое значение > 3 дней.

**Критерий приёмки:** До 30 точек. Ответ за < 1 сек.

### BR-18: Баланс виртуальных счетов и контроль целостности

**Описание:** Отображение балансов виртуальных складов (`VIRTUAL_VENDOR`, `VIRTUAL_LOSS`) и контрольная проверка целостности товарного леджера (dashboard_inventory.md §7.3).

> **Главный принцип системы (BUSINESS.md §1):** «Двойной реестр (товарный + финансовый) должен всегда сохранять целостность — каждое движение товара и каждая денежная операция прослеживаются. Если всё остальное сломается, реестры должны быть корректными.»

**Данные:**

- **Баланс VIRTUAL_VENDOR** — всегда отрицательный, отражает общий объём товара, введённого в систему. По каждому продукту.
- **Баланс VIRTUAL_LOSS** — всегда положительный, отражает общий объём списаний. По каждому продукту.
- **Контрольная сумма:** `|VIRTUAL_VENDOR| - VIRTUAL_LOSS` должно равняться сумме остатков на всех реальных точках (WAREHOUSE + COURIER + CLIENT). Если не сходится — **критический алерт** — ошибка в леджере.
- **Тренд VIRTUAL_LOSS** за 30 дней — растущий тренд = системная проблема (бой, воровство, ошибки учёта)

**Критерий приёмки:** Ответ за < 500 мс. Расхождение контрольной суммы должно быть явно помечено как критическая ошибка.

### BR-19: Загрузка курьеров по дням

**Описание:** Аналитика загрузки курьеров за период — количество доставок на курьера по дням для оценки производительности и планирования ресурсов (dashboard_inventory.md §3.4, dashboard_orders.md §3.4).

**Данные:**

- По каждому курьеру за каждый день периода: количество завершённых доставок
- Агрегаты: общее количество доставок, среднее на курьера, максимальная загрузка
- Фильтр: период (date_from, date_to)

> **Бизнес-контекст (dashboard_orders.md §2.1):** Целевая загрузка курьера — 15-25 заказов в день. Виджет позволяет выявить перегруженных и недозагруженных курьеров.

**Критерий приёмки:** Ответ за < 1 сек.

### BR-20: Выручка по сегментам B2B/B2C

**Описание:** Разбивка выручки и количества заказов по типу клиента — B2B (`client_b2b`) vs B2C (`client_b2c`) за период (dashboard_finance.md §3.3).

> **Бизнес-ценность:** B2B и B2C имеют принципиально разные паттерны (BUSINESS.md §4): B2B — большие объёмы, регулярная периодичность, оплата по договору; B2C — малые объёмы, нерегулярно, наличные/карта. Разделение критично для стратегических решений.

**Данные:**

- По каждому сегменту (`client_b2b`, `client_b2c`): количество завершённых заказов, общая выручка (тийины), средний чек (тийины)
- Учитываются только завершённые заказы (`delivered` / `pickup_completed`)
- **Исключаются** системные пользователи — см. раздел 4.1
- Фильтр: период (date_from, date_to)

**Критерий приёмки:** Ответ за < 500 мс.

## 6. Нефункциональные требования

### NFR-1: Производительность

- Все dashboard-эндпоинты должны отвечать за < 1 секунду при типичной нагрузке (до 10 000 заказов, 100 клиентов, 10 курьеров)
- Summary-эндпоинты (текущие остатки, счётчики) — за < 500 мс

### NFR-2: Масштабируемость

- Аналитические запросы не должны блокировать транзакционные таблицы
- Предусмотреть возможность вынесения агрегатов в materialized views / Redis-кэш в будущем

### NFR-3: Согласованность и свежесть данных

Dashboard показывает данные, консистентные с основными CRUD-операциями. Допустимая задержка зависит от типа данных (dashboard_ux.md §8.1, dashboard_finance.md §7.1):

| Тип данных                                   | Частота обновления                | Механизм                      | Обоснование                                          |
| -------------------------------------------- | --------------------------------- | ----------------------------- | ---------------------------------------------------- |
| KPI-карточки (BR-1 summary, BR-10 summary)   | Каждые 60 сек                     | RTK Query `pollingInterval`   | Операционный мониторинг, допустима минутная задержка |
| Ожидающие подтверждения (PENDING-транзакции) | Каждые 30 сек                     | RTK Query `pollingInterval`   | Рабочая очередь бухгалтера, критичнее чем графики    |
| Аналитические графики (BR-2, BR-6, BR-17)    | При загрузке страницы, кэш 15 мин | RTK Query `keepUnusedDataFor` | Исторические данные, не требуют мгновенности         |
| Aging-бакеты (BR-7)                          | Раз в день или при загрузке       | Ручной запрос                 | Бакеты не меняются чаще, чем раз в сутки             |
| Таблицы с пагинацией (BR-8, BR-12, BR-16)    | По запросу                        | RTK Query on-demand           | Загружаются при навигации или смене фильтра          |
| Карточки курьеров (BR-14)                    | Каждые 60 сек                     | RTK Query `pollingInterval`   | Оперативный мониторинг в течение дня                 |

> **Индикатор свежести (dashboard_ux.md §8.3):** Фронтенд должен показывать timestamp последнего обновления: «Данные на 14:35:22». Зелёный = < 1 мин, жёлтый = 1-5 мин, красный = > 5 мин / потеря соединения.

### NFR-4: Безопасность

- Каждый эндпоинт защищён JWT-аутентификацией
- Доступ ограничен ролевыми scopes (см. раздел 5)
- Кладовщик видит только данные по своим складам

### NFR-5: API-дизайн и граница API/Frontend

**Конвенции API:**

- Все эндпоинты следуют существующим конвенциям проекта (REST, JSON, snake_case)
- Даты в формате ISO 8601 (`2026-04-01`, `2026-04-01T14:30:00+05:00`)

**Граница ответственности API vs Frontend (dashboard_ui.md §9.5):**

API возвращает **raw-данные**. Вся трансформация для отображения — на фронтенде:

| Тип данных       | API возвращает               | Фронтенд показывает                              |
| ---------------- | ---------------------------- | ------------------------------------------------ |
| Суммы            | `12345600` (тийины, BIGINT)  | `123 456 сум` (пробел-разделитель, без копеек)   |
| Суммы в таблицах | `12345600`                   | `123 456,00 сум` или `(123 456 сум)` для расхода |
| Телефоны         | `"998901234567"`             | `+998 90 123-45-67`                              |
| Даты             | `"2026-04-01"` (ISO 8601)    | `01.04.2026` (ДД.ММ.ГГГГ)                        |
| Проценты         | `0.125` (float 0.0-1.0)      | `+12.5%` или `▲ 12.5%`                           |
| Выручка          | `-12345600` (баланс REVENUE) | `123 456 сум` (инвертирован, положительный)      |

> **Принцип:** API не знает о формате отображения. Фронтенд использует утилиты `formatMoney()`, `formatPhone()`, `formatDate()` из дизайн-системы (dashboard_ui.md §11).

## 7. Ограничения и допущения

### Ограничения

- Dashboard API работает исключительно с read-only запросами к PostgreSQL. Никаких записей.
- Все данные извлекаются из существующих таблиц (orders, order_items, transactions, accounts, stock_transfers, stock_transactions, inventory_balances, inventories, users, user_identities, products). Новых таблиц не создаётся.
- Фронтенд отвечает за кэширование на стороне клиента (RTK Query pollingInterval).

### Допущения

- Система обслуживает рынок Узбекистана (BUSINESS.md §1: «Компания работает на рынке Узбекистана»), часовой пояс `Asia/Tashkent` (UTC+5)
- Объём до 500 заказов/день
- Количество курьеров — до 20
- Количество складов — до 10
- Количество клиентов — до 5000
- При данных объёмах все агрегации выполнимы через SQL без предвычисленных таблиц
- Таблица `order_status_history` отсутствует — истинная конверсионная воронка (BR-3) недоступна, используется распределение по текущему статусу
- Поле `is_partial_delivery` отсутствует в модели `Order` — BR-15 требует schema change

## 9. Глоссарий

### Бизнес-термины

| Термин             | Определение                                                                               |
| ------------------ | ----------------------------------------------------------------------------------------- |
| **Тара**           | Пустая возвратная бутыль (~50 000 сум/шт), отслеживается как отдельная товарная единица   |
| **Капитализация**  | Регистрация бутылей у клиента (INITIAL_BALANCE → CLIENT) при отсутствии учтённой тары     |
| **Инкассация**     | Перевод наличных с кассы курьера на кассу компании                                        |
| **DSO**            | Days Sales Outstanding — среднее количество дней до оплаты                                |
| **AOV**            | Average Order Value — средняя сумма заказа                                                |
| **Aging-бакет**    | Группировка долгов по давности (0-7д, 8-14д, ...)                                         |
| **FSM**            | Finite State Machine — конечный автомат статусов заказа                                   |
| **VIRTUAL_VENDOR** | Бесконечный виртуальный источник товара для оприходования                                 |
| **VIRTUAL_LOSS**   | Виртуальное хранилище для списанного/потерянного товара                                   |
| **Тийин**          | Минимальная денежная единица (1 сум = 100 тийин). Все суммы хранятся в тийинах            |
| **SYSTEM_USER**    | Системный пользователь — не является реальным клиентом, исключается из клиентских отчётов |
| **WALKIN_USER**    | Анонимный покупатель для разовых продаж на складе. Баланс обнуляется после каждой продажи |

### Семантика статусов (dashboard_ui.md §5)

Единый маппинг для консистентности между API-ответами и UI-отображением:

| Статус             | Значение enum      | Семантика           | Степень | Контекст                           |
| ------------------ | ------------------ | ------------------- | ------- | ---------------------------------- |
| Новый              | `new`              | Ожидание действия   | info    | Требует назначения курьера         |
| Назначен           | `assigned`         | Подготовка          | info    | Курьер назначен, ожидает выезда    |
| В пути             | `in_transit`       | Активность          | warning | Курьер выехал к клиенту            |
| Прибыл             | `arrived`          | Близко к завершению | warning | Курьер на месте                    |
| Доставлен          | `delivered`        | Успех               | success | Точка невозврата, проводки созданы |
| Самовывоз завершён | `pickup_completed` | Успех               | success | Продажа со склада завершена        |
| Отменён            | `cancelled`        | Негативный исход    | error   | Может быть отменён до доставки     |

| Статус транзакции | Значение    | Семантика                   | Степень |
| ----------------- | ----------- | --------------------------- | ------- |
| Ожидание          | `pending`   | Требует действия бухгалтера | warning |
| Завершена         | `completed` | Балансы обновлены           | success |
| Отклонена         | `rejected`  | Долг остаётся на клиенте    | error   |
