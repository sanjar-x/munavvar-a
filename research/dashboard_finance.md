## 1. Резюме

Данный документ содержит результаты комплексного исследования лучших практик построения финансовых дашбордов для компании MunavvarA (HOD) -- платформы управления доставкой бутилированной воды, работающей на рынке Узбекистана.

### Ключевые выводы

1. **Финансовый дашборд для MunavvarA должен решать 5 критических задач:**
   - Мгновенный обзор финансового здоровья компании (KPI-карточки)
   - Контроль дебиторской задолженности клиентов (B2B и B2C)
   - Мониторинг наличных у курьеров и процесса инкассации
   - Управление потоком подтверждения карточных платежей
   - Прозрачная визуализация движения денежных средств через систему двойной записи

2. **Бэкенд MunavvarA уже содержит все необходимые данные.** Текущая система включает:
   - Модель `FinanceDashboard` с итогами (выручка, касса, долги, ожидания по картам, наличные курьеров)
   - `AccountStatement` -- полноценная банковская выписка с running balance
   - `ClientsDebtsResponse` -- список должников с детализацией
   - `CouriersSummaryResponse` -- сводка по курьерам (собрал/сдал/ожидает)
   - Фильтры по транзакциям (статус, дата, сумма, счёт, заказ)

3. **Рекомендуемый подход:** модульный дашборд с 5-7 KPI-карточками наверху, тремя основными зонами (тренды, задачи, детализация) и ролевым доступом (админ видит всё, бухгалтер -- финансы и подтверждения, кладовщик -- ничего финансового).

## 2. Анализ текущей системы MunavvarA

### 2.1 Архитектура финансового модуля

Текущая система построена на принципе **двойной бухгалтерии** с append-only леджером и PostgreSQL-триггерами для поддержания целостности балансов.

**Типы счетов (`AccountType`):**

| Тип | Назначение | Кто владеет |
|-----|-----------|-------------|
| `REVENUE` | Выручка компании | Система |
| `CASH` | Касса компании (наличные) | Система |
| `CARD` | Безналичные поступления | Система |
| `BANK` | Банковский счёт (резерв) | Система |
| `DISCOUNT` | Скидки | Система |
| `CLIENT` | Лицевой счёт клиента | Каждый клиент |
| `COURIER` | Касса курьера | Каждый курьер |

**Статусы транзакций (`TransactionStatus`):**

| Статус | Назначение |
|--------|-----------|
| `PENDING` | Ожидание подтверждения (карточные платежи) |
| `COMPLETED` | Исполнено (балансы обновлены триггером) |
| `REJECTED` | Отклонено бухгалтером |

### 2.2 Уже реализованные API-эндпоинты (бэкенд)

Бэкенд уже предоставляет данные для:
- **Дашборд** (`get_dashboard`): total_revenue, total_cash_in_hand, total_card_pending, total_client_debt, total_courier_cash, pending_transactions_count
- **Выписка** (`get_account_statement`): opening_balance, closing_balance, running_balance, total_incoming, total_outgoing
- **Должники** (`get_client_debts`): total_debt, debtors_count, список клиентов с балансом и датой последнего платежа
- **Сводка курьеров** (`get_couriers_summary`): по каждому -- баланс, собрано сегодня, сдано сегодня, ожидает сдачи
- **Транзакции** (`get_transactions`): полный фильтруемый журнал с пагинацией
- **Подтверждение/отклонение** (`verify_transaction`, `reject_transaction`): workflow для PENDING-транзакций

### 2.3 Что необходимо добавить для полноценного дашборда

Текущий бэкенд покрывает моментальный снимок, но **не предоставляет:**
- Временные ряды (динамика выручки по дням/неделям/месяцам)
- Aging-бакеты дебиторской задолженности (0-7, 8-14, 15-30, 30+ дней)
- Агрегаты по способам оплаты (доля наличных vs карта vs по договору)
- Топ-должников и топ-клиентов по выручке
- Средний чек и количество заказов за период
- Конверсия подтверждения карточных платежей

## 3. Ключевые финансовые KPI для бизнеса доставки воды

На основе анализа лучших практик из отрасли логистики, дистрибуции и water delivery, а также специфики MunavvarA, рекомендуются следующие группы KPI.

### 3.1 Уровень 1: Стратегические KPI (для CEO/директора)

| KPI | Описание | Формула | Частота |
|-----|----------|---------|---------|
| **Общая выручка** | Совокупный доход от продаж | `-accounts[REVENUE].balance` | Реальное время |
| **Выручка за период** | Доход за день/неделю/месяц | Сумма completed транзакций из REVENUE | День/Неделя/Месяц |
| **Чистый денежный поток** | Разница входящих и исходящих | Приход - Расход за период | День |
| **Средний чек** | Средняя сумма заказа | Выручка / Кол-во заказов | Неделя |
| **Маржинальность доставки** | Доход на одну доставку | Выручка / Кол-во доставок | Месяц |

### 3.2 Уровень 2: Операционные KPI (для бухгалтера/финансиста)

| KPI | Описание | Формула | Частота |
|-----|----------|---------|---------|
| **Общий долг клиентов** | Сумма дебиторской задолженности | `SUM(accounts[CLIENT].balance WHERE balance > 0)` | Реальное время |
| **DSO (Days Sales Outstanding)** | Среднее время до оплаты | Дебиторка / (Выручка / Дней) | Неделя |
| **Наличные в кассе** | Фактический остаток кассы | `accounts[CASH].balance` | Реальное время |
| **Наличные у курьеров** | Деньги "в поле" | `SUM(accounts[COURIER].balance)` | Реальное время |
| **Ожидающие подтверждения (карта)** | Неподтверждённые карточные платежи | `COUNT/SUM(transactions WHERE status=PENDING AND to=CARD)` | Реальное время |
| **Коэффициент инкассации** | % собранных наличных, сданных в кассу | Сдано / Собрано * 100% | День |
| **Процент просроченной задолженности** | Доля просроченных долгов | Просроченная дебиторка / Общая дебиторка * 100% | Неделя |

### 3.3 Уровень 3: Детальные метрики (для аналитики)

| KPI | Описание | Частота |
|-----|----------|---------|
| **Структура оплат** | Разбивка по способам: наличные / карта / по договору | День |
| **Топ-10 должников** | Клиенты с максимальным долгом | Реальное время |
| **Скорость подтверждения карт** | Среднее время от PENDING до COMPLETED/REJECTED | Неделя |
| **Количество ручных проводок** | Индикатор нештатных ситуаций | Неделя |
| **Процент отклонённых платежей** | Rejection rate карточных платежей | Месяц |
| **Выручка по типу клиента** | B2B vs B2C разбивка | Месяц |
| **Aging-бакеты дебиторки** | 0-7 / 8-14 / 15-30 / 31-60 / 60+ дней | Неделя |

## 4. Анализ решений лидеров рынка

### 4.1 Odoo (Accounting Dashboard)

**Компоновка:** Плиточный дашборд с журналами (Customer Invoices, Vendor Bills, Bank, Cash). Каждая плитка показывает баланс журнала и количество незакрытых записей.

**Ключевые элементы:**
- Плитки (tiles) с суммой и количеством по каждому журналу
- Графики Aged Receivables и Aged Payables (горизонтальные столбцы по бакетам)
- Автосверка платежей (95% автоматически, 5% вручную через smart matching)
- Модели сверки для автоматизации повторяющихся операций
- Drill-down из любой плитки в детали

**Что взять для MunavvarA:** Плиточная архитектура с балансами системных счетов, aging-диаграмма для дебиторки, workflow подтверждения с индикатором количества ожидающих.

### 4.2 Zoho Books

**Компоновка:** Вертикальный дашборд с KPI-карточками наверху, графиками в середине, таблицами внизу.

**Ключевые элементы:**
- Карточки: Accounts Receivable, Accounts Payable, Cash Flow, Outstanding Invoices
- График движения денежных средств (area chart)
- Aging Summary по бакетам (0-30, 31-60, 61-90, 90+ дней)
- 40+ стандартных отчётов включая General Ledger
- Реальное время обновления

**Что взять для MunavvarA:** Формат aging summary, стиль KPI-карточек с трендовой стрелкой (рост/падение), интерактивные фильтры по периодам.

### 4.3 QuickBooks

**Компоновка:** Минималистичный дашборд с фокусом на денежном потоке.

**Ключевые элементы:**
- Центральный элемент: Cash Flow waterfall chart (приход -> расход -> баланс)
- Profit & Loss summary card
- Invoices summary (overdue, not yet due, paid last 30 days)
- Банковские счета с реальными балансами
- Expenses breakdown pie chart

**Что взять для MunavvarA:** Waterfall chart для визуализации денежного потока (Выручка -> Касса -> Курьеры -> Клиент), простота подачи информации.

### 4.4 1С:Предприятие / 1С:Управление торговлей

**Компоновка:** Монитор целевых показателей с гистограммами, графиками, диаграммами и конкретными цифрами.

**Ключевые элементы:**
- Панель руководителя с KPI в формате спидометров (gauges)
- План-факт анализ продаж
- ABC-анализ клиентов
- Рабочее место бухгалтера с задачами на подтверждение
- Дашборд дебиторской задолженности с динамикой по периодам

**Релевантный кейс:** Автоматизация доставки воды в группе компаний "Ключ здоровья" на базе 1С: планирование развозов, учёт продаж, отчётность по точкам.

**Что взять для MunavvarA:** Концепция "рабочего места бухгалтера" -- дашборд как список задач (подтвердить платежи, проверить должников, принять инкассацию).

### 4.5 iiko (Syrve) -- ресторанный бизнес + доставка

**Компоновка:** Мобильный + десктоп дашборд с настраиваемыми показателями.

**Ключевые элементы:**
- Cash Balance Report: выручка по кассам, разбивка по типам оплаты, скидки
- Profit & Loss Report: total revenue, expenses, net profit за период
- Cash Flow Statement: входящие/исходящие в реальном времени
- iikoDelivery: аналитика по каждому курьеру, заказу, клиенту
- Мобильный дашборд с динамикой показателей

**Что взять для MunavvarA:** Формат Cash Balance Report идеально ложится на нашу архитектуру (разбивка по типам оплаты + скидки). Концепция "для каждого курьера и каждого клиента" совпадает с нашей моделью персональных счетов.

### 4.6 Специализированные решения для доставки воды

**Trakop (Bottled Water Delivery Software):**
- 6 модулей: заказы, склад, клиенты, платежи, доставка, аналитика
- Pending payment reports -- выделенный отчёт по ожидающим оплатам
- Revenue-wise reports -- выручка с разбивкой по продуктам/маршрутам
- Delivery summary reports -- финансовая сводка по доставкам

**Solid Route Accounting (Prism Visual Software):**
- Cash-out reports и trip reports
- Route profitability -- прибыльность по маршрутам
- Profitability per delivery -- маржа на каждую доставку
- Customer coverage -- охват клиентской базы
- Интеграция с QuickBooks, Sage, SYSPRO

**Что взять для MunavvarA:** Выделенный раздел "Ожидающие платежи" как центральный элемент рабочего места бухгалтера. Отчёт о прибыльности по маршрутам/курьерам.

## 5. Рекомендации по типам графиков и визуализации

### 5.1 Матрица соответствия "Данные -> Тип графика"

| Данные MunavvarA | Рекомендуемый тип | Почему |
|------------------|-------------------|--------|
| **Динамика выручки** | Line Chart (линейный график) | Показывает тренды и сезонность во времени. Исследования подтверждают: line chart -- стандарт для трендового анализа |
| **Структура оплат** (наличные/карта/договор) | Donut Chart (кольцевая диаграмма) | Показывает долю каждого способа в общем объёме. Максимум 4-5 сегментов |
| **Aging дебиторки** | Horizontal Stacked Bar Chart | Стандарт индустрии (Odoo, Zoho, NetSuite). Бакеты по времени, цветовая кодировка по сроку просрочки |
| **Денежный поток** | Waterfall Chart | Показывает как начальный баланс трансформируется в конечный через цепочку операций. Идеален для Cash Flow |
| **Движение денег между счетами** | Sankey Diagram | Визуализирует потоки: Выручка -> Клиент -> Курьер -> Касса. Ширина линии пропорциональна сумме |
| **Баланс кассы / курьеров** | KPI Cards со sparkline | Число с микрографиком тренда за последние 7 дней |
| **Топ-должники** | Horizontal Bar Chart | Ранжированный список по сумме долга, легко читается |
| **Ежедневная выручка vs цель** | Bar Chart + Target Line | Столбцы по дням + горизонтальная линия плана |
| **Статусы подтверждений** | Stacked Bar Chart или Pie | Pending / Completed / Rejected за период |
| **Выписка по счёту** | Table с running balance | Классический табличный формат банковской выписки |

### 5.2 Цветовая палитра

```
Доход / Приход / Положительное  -> #22C55E (зелёный)
Расход / Долг / Отрицательное   -> #EF4444 (красный)
Ожидание / Pending              -> #F59E0B (жёлтый/оранжевый)
Нейтральное / Информация        -> #3B82F6 (синий)
Отклонено / Rejected            -> #6B7280 (серый)
```

### 5.3 Правила визуализации

1. **Ось Y всегда начинается с нуля** -- предотвращает визуальное искажение данных
2. **Не более 5-7 KPI на главном экране** -- исследования показывают, что более 8 метрик снижают восприятие
3. **Суммы в узбекских сумах отображать в формате "1 250 000 сум"** -- с разделителем тысяч и единицей валюты
4. **Суммы в тийинах конвертировать в сумы для отображения** -- деление на 100 с двумя знаками после запятой
5. **Использовать трендовые стрелки** -- рост/падение по сравнению с предыдущим периодом (день/неделя)
6. **Цветовая индикация отклонений** -- красный фон если долг растёт, зелёный если падает

## 6. Макет и компоновка дашборда

### 6.1 Принципы компоновки (на основе UX-исследований)

**F-паттерн чтения (eye-tracking):**
Пользователь сканирует дашборд по F-паттерну: сначала горизонтально по верхнему ряду, затем вниз по левой стороне. Критические KPI размещаются в верхнем левом углу.

**Z-паттерн для руководителей:**
Для executive-дашбордов, где важна скорость, подходит Z-паттерн: слева направо по верху, диагонально вниз, слева направо по низу.

**Правило 40-30-20-10:**
- 40% экрана -- главная метрика (выручка или денежный поток)
- 30% -- 2-3 вторичных KPI
- 20% -- контекст (sparklines, сравнения)
- 10% -- навигация и фильтры

## 7. Real-time vs Периодическая отчётность

### 7.1 Анализ частоты обновления для MunavvarA

| Данные | Рекомендация | Обоснование |
|--------|-------------|-------------|
| Баланс кассы | **Real-time** (при каждой транзакции) | Бухгалтер должен видеть актуальный остаток |
| Наличные у курьеров | **Real-time** | Критично для инкассации и контроля |
| Ожидающие подтверждения | **Real-time** | Это рабочая очередь бухгалтера |
| Общий долг клиентов | **Real-time** (по запросу, без автообновления) | Меняется при каждой доставке |
| Выручка за день | **Реалтайм-накопление** | Обновляется при каждом COMPLETED заказе |
| Динамика выручки (график) | **Периодически** (каждые 15 мин или при переходе на страницу) | Нет смысла обновлять каждую секунду |
| Aging дебиторки | **Периодически** (раз в день) | Бакеты не меняются чаще, чем раз в сутки |
| DSO и другие расчётные KPI | **Ежедневно/Еженедельно** | Требуют агрегации за период |

### 7.2 Техническая реализация

**Рекомендуемый подход: "Smart Refresh"**

1. **KPI-карточки** -- загружаются при открытии страницы, обновляются каждые 60 секунд или по нажатию кнопки "Обновить"
2. **Графики** -- загружаются при открытии, кэшируются на 15 минут, обновляются при смене фильтра периода
3. **Таблица ожидающих подтверждений** -- polling каждые 30 секунд (или WebSocket для мгновенных обновлений)
4. **Таблицы с пагинацией** (транзакции, должники) -- загружаются по запросу

**Индикатор свежести данных:** Обязательно отображать timestamp последнего обновления: "Данные на 14:35:22" -- это стандарт лучших практик (Phoenix Strategy Group, SimplеKPI).

## 8. Управление дебиторской задолженностью

### 8.1 Специфика дебиторской задолженности MunavvarA

В системе MunavvarA дебиторская задолженность формируется тремя путями:

1. **Карточные платежи до подтверждения** -- клиент заплатил картой, но бухгалтер ещё не подтвердил. Формально клиент "должен" до момента подтверждения.
2. **B2B-клиенты по договору** -- долг накапливается сознательно, оплата по условиям контракта.
3. **Неоплаченные доставки** -- редкая ситуация, когда доставка завершена, но оплата не прошла.

### 8.2 Рекомендуемый дашборд дебиторской задолженности

**Верхний ряд -- агрегаты:**
```
+------------------------------------------------------------------+
| Общий долг: 15 750 000 сум | Должников: 47 | DSO: 12.3 дня      |
+------------------------------------------------------------------+
```

**Средняя часть -- Aging Analysis:**

Aging-бакеты рекомендуется адаптировать под специфику бизнеса:

| Бакет | Стандарт отрасли | Рекомендация для MunavvarA |
|-------|-----------------|---------------------------|
| Current | 0-30 дней | **0-7 дней** (цикл заказа воды -- 3-7 дней) |
| Warning | 31-60 дней | **8-14 дней** (второй цикл) |
| Overdue | 61-90 дней | **15-30 дней** |
| Critical | 90+ дней | **31-60 дней** |
| Bad Debt | - | **60+ дней** (потенциальное списание) |

Обоснование: стандартные 30-дневные бакеты (как в QuickBooks, Zoho) слишком грубые для бизнеса с недельным циклом заказов. Клиент, не плативший 14 дней, -- уже проблема.

**Визуализация aging:**
- Horizontal stacked bar chart с цветовой кодировкой (зелёный -> жёлтый -> оранжевый -> красный -> тёмно-красный)
- Каждый сегмент кликабелен -- drill-down в список клиентов в этом бакете

**Нижняя часть -- Таблица должников:**

| Клиент | Тип | Телефон | Долг | Последний платёж | Дней без оплаты | Действия |
|--------|-----|---------|------|-----------------|-----------------|----------|
| ООО "Аквамир" | B2B | +998... | 2 500 000 | 15.03.2026 | 17 | [Выписка] [Связаться] |
| Фаррух Х. | B2C | +998... | 150 000 | 28.03.2026 | 4 | [Выписка] |

**Фильтры:**
- По типу клиента (B2B / B2C / Все)
- По минимальной сумме долга
- По количеству дней без оплаты
- Сортировка по сумме / дате / имени

### 8.3 Метрики AR по лучшим практикам (Tratta, NetSuite, HighRadius)

- **DSO (Days Sales Outstanding)** -- среднее время от создания долга до оплаты
- **CEI (Collection Effectiveness Index)** -- процент собранных средств: `(Начальный баланс + Продажи за период - Конечный баланс) / (Начальный баланс + Продажи за период) * 100%`
- **ADD (Average Days Delinquent)** -- среднее количество дней просрочки: `DSO - Best Possible DSO`
- **Bad Debt Ratio** -- процент списанной задолженности
- **AR Turnover Ratio** -- скорость оборота дебиторки: `Выручка / Средняя дебиторка`

## 9. Мониторинг инкассации (касса курьеров)

### 9.1 Контекст

В MunavvarA каждый курьер имеет персональную "кассу" (счёт типа `COURIER`). При оплате наличными деньги проходят путь:

```
Выручка -> Клиент (долг) -> Курьер (сбор) -> Касса компании (инкассация)
```

Критично отслеживать:
- Сколько наличных у каждого курьера прямо сейчас
- Какая доля собранных денег уже инкассирована
- Есть ли курьеры с аномально высоким балансом

### 9.2 Рекомендуемый дашборд курьеров

**Формат -- карточки по курьерам (как в iiko):**

```

+------------------------------------------------------------------+
|                                                                    |
|  +---------------------------+  +---------------------------+      |
|  | Иванов Пётр               |  | Каримов Алишер            |      |
|  | Баланс: 850 000           |  | Баланс: 720 000           |      |
|  | Собрано сегодня: 1 200 000|  | Собрано сегодня: 900 000  |      |
|  | Сдано сегодня: 350 000    |  | Сдано сегодня: 180 000    |      |
|  | [Инкассация]              |  | [Инкассация]              |      |
|  +---------------------------+  +---------------------------+      |
|                                                                    |
|  +---------------------------+  +---------------------------+      |
|  | Рахимов Бахром             |  | Ахмедов Дильшод           |      |
```

**Важные индикаторы:**

### 9.3 Процесс инкассации в UI

Администратор или бухгалтер должен иметь возможность прямо из дашборда:
1. Нажать "Инкассация" на карточке курьера
2. Указать сумму (по умолчанию -- весь баланс)
3. Подтвердить -- создаётся проводка Курьер -> Касса (COMPLETED)
4. Карточка обновляется в реальном времени

## 10. Сверка платежей по карте (Pending Payments)

### 10.1 Специфика MunavvarA

Карточные платежи в MunavvarA проходят через двухэтапный процесс:
1. При доставке/самовывозе с оплатой картой создаётся транзакция Клиент -> Карта со статусом `PENDING`
2. Бухгалтер проверяет факт поступления средств и подтверждает (`COMPLETED`) или отклоняет (`REJECTED`)

Пока транзакция в `PENDING` -- балансы счетов **не обновляются**. Клиент продолжает числиться должником.

### 10.2 Рекомендуемый UI для сверки

**Лучшие практики из Odoo, Worldpay, Osfin:**

**Верхняя панель -- статистика:**
```
+------------------------------------------------------------------+
| Ожидают подтверждения: 5 транзакций на сумму 2 150 000 сум       |
| Средний возраст ожидания: 4.2 часа                                |
| Самая старая: 18 часов (ВНИМАНИЕ!)                                |
+------------------------------------------------------------------+
```

**Основная таблица -- список PENDING-транзакций:**

| # | Дата/время | Клиент | Заказ | Сумма | Ожидает | Действия |
|---|-----------|--------|-------|-------|---------|----------|
| 1 | 01.04 09:15 | Фаррух Х. | #456 | 150 000 | 5ч 20м | [Подтвердить] [Отклонить] |
| 2 | 01.04 10:30 | ООО "Аква" | #457 | 500 000 | 4ч 05м | [Подтвердить] [Отклонить] |
| 3 | 01.04 11:45 | Олим М. | #458 | 200 000 | 2ч 50м | [Подтвердить] [Отклонить] |

**Функциональность:**
- **Массовое подтверждение** -- чекбоксы + кнопка "Подтвердить выбранные" для пакетной обработки
- **Сортировка по возрасту** -- самые старые наверху (по умолчанию)
- **Цветовая индикация возраста:** < 2ч -- нейтральный, 2-8ч -- жёлтый, > 8ч -- красный
- **При отклонении** -- модальное окно с обязательным полем "Причина"
- **Drill-down в заказ** -- клик на номер заказа открывает карточку заказа

### 10.3 Workflow подтверждения (на основе Odoo reconciliation)

```
PENDING (создана при доставке)
    |
    v
Бухгалтер открывает дашборд
    |
    v
Проверяет банковскую выписку / SMS / мобильный банк
    |
    +---> [Подтвердить] -> COMPLETED (триггер обновляет балансы)
    |
    +---> [Отклонить + причина] -> REJECTED (долг остаётся на клиенте)
```

### 10.4 Уведомления

- **Badge на вкладке "Финансы"** -- количество PENDING-транзакций
- **Уведомление при новом PENDING** -- если реализован WebSocket/polling
- **Ежедневный отчёт** -- количество PENDING старше 24 часов

## 11. Визуализация двойной бухгалтерии

### 11.1 Проблема

Двойная бухгалтерия -- мощная система, но **контринтуитивна для нефинансистов.** Например:
- Баланс счёта "Выручка" всегда **отрицательный** (деньги "уходят" из выручки)
- Клиентский долг -- это **положительный** баланс на счёте клиента
- Одна операция доставки генерирует 2-3 проводки

### 11.2 Стратегия визуализации

**Принцип: скрыть механику, показать результат.**

Пользователь (бухгалтер/админ) не должен думать в терминах дебета/кредита. Вместо этого:

1. **Выручку показывать как положительное число** (в бэкенде уже реализовано: `total_revenue = -revenue_balance`)
2. **Долг клиента -- как "Задолженность"** (положительное число = "клиент должен нам")
3. **Кассу курьера -- как "Наличные на руках"**
4. **Проводки показывать как "Клиент заплатил 150 000 наличными"**, а не "Дебет: Касса курьера, Кредит: Счёт клиента"

### 11.3 Sankey-диаграмма для визуализации потоков

Для продвинутой аналитики рекомендуется **Sankey-диаграмма** -- визуализация движения денег через все счета:

```
    Выручка (45.2M)
        |
        +---> Клиенты B2C (25.1M) ---> Курьеры (22.0M) ---> Касса (20.5M)
        |                          |
        |                          +--> Карта (3.1M)
        |
        +---> Клиенты B2B (15.8M) ---> Касса (8.2M)
        |                          |
        |                          +--> Карта (7.6M)
        |
        +---> Walk-in (4.3M) -------> Касса (4.3M)
```

Ширина каждого потока пропорциональна сумме. Это мгновенно показывает:
- Какой канал генерирует больше выручки
- Какая доля оплачивается наличными vs картой
- Сколько денег "застревает" в дебиторке

### 11.4 Выписка как "человеческий" формат двойной записи

Вместо показа raw-проводок (from_id -> to_id) рекомендуется формат **банковской выписки:**

```
+------------------------------------------------------------------+
| Выписка по счёту: Касса компании                                   |
| Период: 01.03.2026 - 31.03.2026                                   |
| Входящий остаток: 5 200 000 сум                                   |
+------------------------------------------------------------------+
| Дата     | Описание                    | Приход    | Расход | Остаток |
|----------|----------------------------|-----------|--------|---------|
| 01.03    | Инкассация: Иванов П.      | 1 200 000 |        | 6 400 000|
| 02.03    | Оплата наличными: Клиент А | 150 000   |        | 6 550 000|
| 03.03    | Возврат клиенту: Клиент Б  |           | 50 000 | 6 500 000|
| ...      | ...                        | ...       | ...    | ...     |
+------------------------------------------------------------------+
| Итого приход: 12 500 000 | Итого расход: 3 200 000               |
| Исходящий остаток: 14 500 000 сум                                 |
+------------------------------------------------------------------+
```

Этот формат уже поддерживается бэкендом (`AccountStatement` с `StatementEntry`), нужно только реализовать фронтенд.

**Дополнительные рекомендации:**

- Пагинация с показом общего количества записей

### 13.4 Специфические паттерны для узбекского рынка

1. **Формат валюты:** `1 250 000 сум` -- пробел как разделитель тысяч, слово "сум" после числа
2. **Конвертация тийинов:** Все суммы хранятся в тийинах (1 сум = 100 тийин), на фронтенде делим на 100 и показываем без копеек (для крупных сумм) или с двумя знаками (для аналитики)
3. **Формат телефона:** +998 XX XXX-XX-XX
4. **Формат даты:** ДД.ММ.ГГГГ ЧЧ:ММ
5. **Язык интерфейса:** Русский (основной) с возможностью переключения на узбекский
6. **Большие числа:** Использовать сокращения для графиков: "1.2 млн", "45.2 млн"

### 13.5 Mobile-first соображения

Бухгалтер и администратор могут проверять дашборд с мобильного устройства. Критичные элементы для мобильной версии:

1. **KPI-карточки** -- должны складываться в одну колонку (2x3 вместо 3x2)
2. **Таблица ожидающих подтверждений** -- swipe-действия (свайп вправо = подтвердить, свайп влево = отклонить)
3. **Список должников** -- карточный формат вместо таблицы на узких экранах
4. **Графики** -- упрощённые версии (sparkline вместо полных графиков)

## 14. Дорожная карта реализации

### Фаза 1: MVP финансового дашборда (1-2 недели)

**Цель:** Рабочий инструмент бухгалтера

- [ ] KPI-карточки (6 штук): Выручка, Касса, Долг клиентов, Ожидающие карточные, Наличные у курьеров, Pending count
- [ ] Таблица ожидающих подтверждений с кнопками Подтвердить/Отклонить
- [ ] Список должников с фильтром по минимальной сумме
- [ ] Выписка по счёту (табличный формат)

**Источники данных:** Все API уже готовы в бэкенде.

### Фаза 2: Операционные инструменты (1-2 недели)

**Цель:** Полный набор инструментов для ежедневной работы

- [ ] Сводка по курьерам (карточки) с кнопкой инкассации
- [ ] Журнал транзакций с фильтрами и пагинацией
- [ ] Список счетов с drill-down в выписку
- [ ] Приём оплаты от клиента (форма кассира)
- [ ] Создание ручной проводки (форма)

### Фаза 3: Аналитика и графики (2-3 недели)

**Цель:** Визуальная аналитика для принятия решений

- [ ] Новые API-эндпоинты (revenue-trend, debt-aging, payment-methods)
- [ ] Line chart динамики выручки (по дням за 30 дней)
- [ ] Stacked bar chart aging дебиторки
- [ ] Donut chart структуры оплат
- [ ] Bar chart + target line (план/факт выручки, если добавлен механизм целей)

### Фаза 4: Продвинутая аналитика (3-4 недели)

**Цель:** Стратегические инструменты для руководства

- [ ] Sankey-диаграмма денежных потоков
- [ ] Расчётные KPI: DSO, CEI, AR Turnover
- [ ] Сравнение периодов (этот месяц vs прошлый)
- [ ] Экспорт отчётов в Excel/PDF
- [ ] Настраиваемый дашборд (drag-and-drop виджетов)
