## 1. Резюме для руководства (Executive Summary)

Настоящий документ содержит результаты комплексного исследования лучших практик проектирования дашборда складского учёта для платформы MunavvarA (HOD) — системы управления доставкой бутилированной воды.

### Ключевые выводы

1. **Возвратная тара — центральный объект учёта.** В отличие от классических WMS, MunavvarA оперирует возвратными активами (бутылями), которые непрерывно циркулируют между складами, курьерами и клиентами. Дашборд должен визуализировать полный цикл жизни бутыли — от поставщика до клиента и обратно.

2. **Двухуровневый мониторинг.** Необходимо отслеживать одновременно два потока: (а) физический товар (вода, тара, оборудование) и (б) финансовые последствия каждого перемещения. Это уникальная черта MunavvarA — двойной реестр (товарный + финансовый).

3. **Курьер как мобильный склад.** Каждая машина курьера — это отдельная складская точка с собственными остатками. Дашборд должен поддерживать real-time мониторинг загрузки каждого курьера в течение дня.

4. **Сверка при закрытии смены — критический бизнес-процесс.** Интерфейс инвентаризации и закрытия смены должен быть максимально простым и однозначным, так как расхождения блокируют процесс.

5. **Append-only реестр.** Все складские транзакции неизменяемы — исправления через компенсирующие перемещения. Дашборд должен показывать полную историю движения без возможности «стереть» записи.

## 2. Ключевые KPI для складского дашборда MunavvarA

На основании анализа лучших практик (NetSuite, Hopstack, MRPeasy, Deskera) и специфики бизнеса доставки воды, рекомендуются следующие KPI:

### 2.1 Критические KPI (отображать на главном экране — Summary Tiles)

| #   | KPI                                    | Формула / описание                                                                            | Почему важен для MunavvarA                                           |
| --- | -------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | **Общий остаток воды (полные бутыли)** | SUM(quantity) WHERE product.type = 'water' AND inventory.type IN ('WAREHOUSE', 'COURIER')     | Главный операционный показатель — сколько воды доступно для доставки |
| 2   | **Общий остаток тары (пустые бутыли)** | SUM(quantity) WHERE product.type = 'container' AND inventory.type IN ('WAREHOUSE', 'COURIER') | Тара — дорогой актив (~50,000 сум/шт), её потеря — прямые убытки     |
| 3   | **Тара у клиентов**                    | SUM(quantity) WHERE product.type = 'container' AND inventory.type = 'CLIENT'                  | Показывает объём тары «в обороте» у клиентов, подлежащей возврату    |
| 4   | **Товар на курьерах (в пути)**         | SUM(quantity) WHERE inventory.type = 'COURIER'                                                | Сколько товара сейчас на машинах, ещё не доставлено                  |
| 5   | **Потери (за период)**                 | SUM(quantity) WHERE transfer.type = 'LOSS_WRITE_OFF' AND period = current                     | Объём списаний — индикатор проблем (бой, воровство, ошибки)          |
| 6   | **Точность складского учёта**          | (Кол-во сверок без расхождений / Общее кол-во сверок) \* 100%                                 | Целевой показатель >= 99%. Отражает качество учёта                   |

### 2.2 Оперативные KPI (второй уровень)

| #   | KPI                             | Формула / описание                                                           | Частота обновления        |
| --- | ------------------------------- | ---------------------------------------------------------------------------- | ------------------------- |
| 7   | **Оборачиваемость запасов**     | Кол-во доставленных единиц за период / Средний остаток на складах            | Ежедневно / еженедельно   |
| 8   | **Дни запаса (Days of Supply)** | Текущий остаток / Средний дневной расход                                     | Real-time                 |
| 9   | **Скорость загрузки курьера**   | Время от создания COURIER_LOAD до завершения                                 | Ежедневно                 |
| 10  | **Скорость возврата курьера**   | Время от последней доставки до COURIER_RETURN                                | Ежедневно                 |
| 11  | **Процент возврата тары**       | (Кол-во возвращённой тары / Кол-во выданной тары) \* 100%                    | Ежедневно                 |
| 12  | **Расхождения при сверке**      | Абсолютная разница между системными и фактическими остатками                 | При каждом закрытии смены |
| 13  | **Капитализация тары**          | SUM(quantity) WHERE transfer.type = 'INITIAL_BALANCE' AND to.type = 'CLIENT' | Ежедневно                 |
| 14  | **Коэффициент потерь**          | (Потери за период / Общий оборот) \* 100%                                    | Еженедельно / ежемесячно  |

### 2.3 Стратегические KPI (ежемесячная / квартальная аналитика)

| #   | KPI                                   | Описание                                                                              |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------- |
| 15  | **Стоимость хранения**                | Затраты на содержание единицы товара на складе (включая аренду, зарплату кладовщика)  |
| 16  | **Соотношение полных/пустых бутылей** | Баланс между заполненной водой тарой и пустыми бутылями в системе                     |
| 17  | **Средний дефицит тары на клиента**   | Средний объём автоматической капитализации тары при создании заказа                   |
| 18  | **Баланс виртуального поставщика**    | Чистый объём товара, введённого в систему через VIRTUAL_VENDOR (всегда отрицательный) |

### 4.3 Размеры тайлов (Summary Cards)

Опираясь на лучшие практики (Odoo, Microsoft Dynamics 365, Bold BI):

- **Не более 6 тайлов** в одном ряду на экране обзора
- Каждый тайл: иконка + числовое значение + мини-тренд (спарклайн) + процент изменения за период
- Клик на тайл — переход к детальному отчёту по этому KPI
- Цветовая рамка или фон тайла отражает статус (норма/предупреждение/критично)

## 6. Подходы к обновлению данных: Real-time vs Batch

### 6.1 Рекомендация для MunavvarA: Гибридный подход

Учитывая архитектуру MunavvarA (PostgreSQL-триггеры обновляют `inventory_balances` при каждом INSERT в `stock_transactions`), система уже реализует **real-time обновление остатков на уровне базы данных**.

| Данные                     | Подход                                          | Обоснование                                               |
| -------------------------- | ----------------------------------------------- | --------------------------------------------------------- |
| Текущие остатки по складам | **Real-time**                                   | Триггер `update_inventory_balances()` обновляет мгновенно |
| Остатки на курьерах        | **Real-time**                                   | Критично для оперативного контроля доставки               |
| Summary Tiles (KPI)        | **Near real-time** (polling 30-60 сек)          | Агрегированные запросы; допустима задержка                |
| Графики трендов            | **Batch** (1 раз в час / при загрузке страницы) | Исторические данные, не требуют мгновенности              |
| Журнал перемещений         | **Real-time** (при открытии страницы + polling) | Оперативный мониторинг                                    |
| Алерты (низкий запас)      | **Event-driven** (при каждом перемещении)       | Немедленное уведомление                                   |
| Отчёт по должникам тары    | **Batch** (1 раз в день / по запросу)           | Аналитический отчёт                                       |

### 6.2 Технические рекомендации

1. **Backend API:** Отдельные эндпоинты для дашборда с агрегированными данными (не тянуть все записи на фронт)
2. **RTK Query (фронтенд):** Использовать `pollingInterval` для автообновления тайлов (30-60 сек)
3. **Кэширование:** Агрегированные KPI кэшировать в Redis (когда будет подключён) с инвалидацией при INSERT в `stock_transactions`
4. **WebSocket (будущее):** Для push-уведомлений о критических событиях (нулевой остаток, расхождение при сверке)

## 7. Специфические рекомендации для MunavvarA

### 7.1 Учёт тары (Container Tracking) — приоритет #1

Тара — самый ценный физический актив бизнеса. Каждая бутыль стоит ~50,000 сум, при объёме 5,000+ бутылей это 250+ млн сум замороженного капитала.

**Рекомендуемые виджеты:**

1. **«Карта тары» (Container Map)** — визуализация распределения тары по всем точкам системы:
   - Склады (WAREHOUSE) — тара на хранении
   - Курьеры (COURIER) — тара в пути
   - Клиенты (CLIENT) — тара в обороте
   - Потери (VIRTUAL_LOSS) — безвозвратные потери
   - Показывать в виде Donut-диаграммы или Waterfall-диаграммы

2. **«Возвратность тары» (Return Rate Tracker)** — ежедневный/недельный показатель процента возврата тары:
   - Цель: >= 95%
   - Тренд за 30 дней (Line Chart)
   - Алерт при падении ниже 90%

3. **«Должники по таре» (Container Debtors)** — таблица клиентов с наибольшим объёмом невозвращённой тары:
   - Колонки: Клиент, Тип (B2C/B2B), Кол-во тары на балансе, Дней с последнего заказа
   - Сортировка по убыванию кол-ва
   - Фильтр: показать только тех, кто не заказывал > 14 дней (риск невозврата)

4. **«Капитализация тары» (Tara Capitalization Log)** — мониторинг операций INITIAL_BALANCE→CLIENT:
   - Объём за день/неделю/месяц
   - Разделение: автоматическая (при заказе) vs ручная (администратором)
   - Тренд роста — индикатор, что всё больше клиентов входят без учтённой тары

### 7.2 Мониторинг курьеров (Courier Vehicle Stock) — приоритет #2

**Рекомендуемые виджеты:**

1. **«Курьеры на линии» (Active Couriers)** — список курьеров с активным транспортом:
   - Формат: карточки (Card Grid)
   - На каждой карточке: имя, номер машины, текущий остаток (вода / пустая тара / оборудование), прогресс доставок (12/15), сумма собранных наличных
   - Цветовая индикация: зелёный (всё ок), жёлтый (мало товара), красный (нужно подгрузить)

2. **«Загрузка vs Возврат» (Load vs Return Analysis)** — сопоставление утренней загрузки с вечерним возвратом:
   - Grouped Bar Chart по каждому курьеру
   - Разница = доставлено клиентам + потери
   - Визуальное выявление аномалий (если возврат слишком мал для кол-ва доставок)

3. **«Готовность к закрытию смены» (Shift Readiness)** — индикатор для каждого курьера:
   - Все заказы доставлены? (да/нет)
   - Наличные сверены? (да/нет)
   - Остатки совпадают с системой? (да/нет/не проверено)

### 7.3 Виртуальные склады (VIRTUAL_VENDOR / VIRTUAL_LOSS) — приоритет #3

**Рекомендуемые виджеты:**

1. **«Баланс Virtual Vendor»** — большое число с трендом:
   - Всегда отрицательный (показывает общий объём товара, введённого в систему)
   - Резкое изменение = массовое оприходование (нормально) или ошибка (нужно проверить)

2. **«Баланс Virtual Loss»** — большое число с трендом:
   - Всегда положительный (показывает общий объём списаний)
   - Растущий тренд = системная проблема (бой, воровство)
   - Разбивка по причинам списания (reason из StockTransfer)

3. **«Чистый баланс системы» (System Net Balance)** — контрольная сумма:
   - |VIRTUAL_VENDOR| - VIRTUAL_LOSS = Товар в обороте (склады + курьеры + клиенты)
   - Если не сходится — ошибка в леджере (критический алерт)

### 7.4 Сверка и закрытие смены (Shift Reconciliation) — приоритет #4

**Рекомендуемые виджеты:**

1. **«Панель закрытия смены» (Shift Closing Panel)** — специальный интерфейс:

   ```
   +----------------------------------------------------------+
   | ЗАКРЫТИЕ СМЕНЫ: Курьер Алишер | Машина 01A123BC          |
   +----------------------------------------------------------+
   | ТОВАР         | СИСТЕМА | ФАКТ | РАЗНИЦА | СТАТУС        |
   |---------------|---------|------|---------|---------------|
   | Вода Hayot    |    5    |  5   |    0    | OK            |
   | Вода MunavvarA|    3    |  2   |   -1    | РАСХОЖДЕНИЕ   |
   | Тара Hayot    |   18    |  18  |    0    | OK            |
   | Тара MunavvarA|   12    |  13  |   +1    | РАСХОЖДЕНИЕ   |
   +----------------------------------------------------------+
   | [!] СМЕНУ НЕЛЬЗЯ ЗАКРЫТЬ: 2 расхождения                  |
   | [Оформить списание (-1 Вода MunavvarA)]                  |
   | [Оформить находку (+1 Тара MunavvarA)]                   |
   +----------------------------------------------------------+
   | ПОСЛЕ КОРРЕКТИРОВКИ:                                     |
   | [ ] Вернуть остатки на склад                             |
   | [ ] Провести инкассацию (750,000 сум)                    |
   | [ ] Деактивировать транспорт                             |
   |                                                          |
   | [ЗАКРЫТЬ СМЕНУ]                                          |
   +----------------------------------------------------------+
   ```

2. **«История сверок» (Reconciliation History)** — таблица всех закрытий смен:
   - Колонки: Дата, Курьер, Расхождений, Списано, Найдено, Время закрытия
   - Фильтр по курьеру и периоду
   - Выделение строк с расхождениями

3. **«Статистика расхождений» (Discrepancy Stats)** — аналитика по качеству учёта:
   - Процент смен без расхождений (цель: 95%+)
   - Самые частые товары с расхождениями
   - Курьеры с наибольшим количеством расхождений

## 8. Примеры из реального мира и референсы

### 8.1 Beverage Distribution (Prism VS, Omnna)

Платформы для дистрибуции напитков (Prism Visual Software, Omnna DMS) реализуют:

- Отслеживание возвратных контейнеров (кеги, ящики) по серийным номерам
- Автоматический расчёт залога при выдаче и кредита при возврате
- Дашборд с циркуляцией контейнеров: сколько выдано, сколько вернулось, сколько «зависло»
- Real-time inventory across warehouses and delivery vehicles

**Применение для MunavvarA:** Адаптировать концепцию «циркуляции контейнеров» для тары, с визуализацией полного цикла жизни бутыли.

### 8.2 Rekart (Empty Bottle Tracking)

Специализированная платформа для учёта пустых бутылей в молочной и водной доставке:

- Backend-дашборд показывает: бутыли в циркуляции, невозвращённые бутыли, депозитные балансы по клиентам
- При возврате пустой бутыли система автоматически кредитует клиента
- Live-отчёт: сколько бутылей в обороте, у каких клиентов просрочен возврат, сколько стоимости заморожено в невозвращённых активах

**Применение для MunavvarA:** Прямая аналогия с моделью тары. Рекомендуется виджет «Стоимость тары у клиентов» (кол-во \* 50,000 сум = замороженный капитал).

### 8.3 TrackAbout (Returnable Container Tracking)

Глобальная платформа для управления возвратными контейнерами:

- RFID/Barcode отслеживание каждого контейнера
- Дашборд: местоположение, содержимое, состояние каждого контейнера
- Аналитика срока службы контейнера
- Оповещения о просроченных возвратах

**Применение для MunavvarA:** В будущем — переход от количественного учёта к поштучному (RFID/QR на каждой бутыли), но для MVP достаточно количественного учёта по типам тары.

### 8.4 Водяной (Vodasoft) — российский аналог

Специализированная программа для водных компаний:

- Учёт тары у клиентов (своя, залоговая, арендная)
- Учёт остатков в машинах и на складах
- Десятки отчётов: продажи, доставка, водители, новые клиенты, тара, недоставленные заказы
- Мобильное приложение для курьеров

**Применение для MunavvarA:** Референсная модель для функциональности, но MunavvarA уже превосходит по архитектуре (двойной реестр, append-only леджер, PG-триггеры).

## 11. Техническое соответствие архитектуре MunavvarA

### 11.1 Маппинг KPI на существующие модели

| KPI                   | Таблица / Модель                            | Запрос                                                                          |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------- |
| Общий остаток воды    | `inventory_balances` JOIN `products`        | WHERE products.type = 'water' AND inventories.type IN ('WAREHOUSE', 'COURIER')  |
| Тара у клиентов       | `inventory_balances` JOIN `inventories`     | WHERE inventories.type = 'CLIENT' AND products.type = 'container'               |
| Потери за период      | `stock_transactions` JOIN `stock_transfers` | WHERE transfers.type = 'LOSS_WRITE_OFF' AND created_at >= period_start          |
| Оборачиваемость       | `stock_transactions`                        | SUM(quantity) WHERE type = 'CLIENT_DELIVERY' / AVG(inventory_balances.quantity) |
| Процент возврата тары | `stock_transactions`                        | COUNT(CLIENT_RETURN) / COUNT(CLIENT_DELIVERY) для container products            |
| Баланс VIRTUAL_VENDOR | `inventory_balances`                        | WHERE inventory.type = 'VIRTUAL_VENDOR'                                         |

### 11.2 Предложения по новым индексам

```sql
-- Для быстрой агрегации остатков по типу инвентаря
CREATE INDEX idx_inv_balances_inv_type
ON inventory_balances (inventory_id)
INCLUDE (product_id, quantity);

-- Для быстрого подсчёта перемещений по типу за период
CREATE INDEX idx_stock_transfers_type_date
ON stock_transfers (type, created_at)
WHERE status = 'COMPLETED';

-- Для поиска клиентов-должников по таре
CREATE INDEX idx_inv_balances_client_containers
ON inventory_balances (inventory_id, quantity)
WHERE quantity > 0;
```

### 11.3 Рекомендации по API-эндпоинтам

Все эндпоинты дашборда должны возвращать **агрегированные данные** (не raw-записи), чтобы минимизировать нагрузку на фронтенд:

```python
# Пример схемы ответа для главного дашборда
class InventoryDashboardSummary(BaseModel):
    total_water_stock: int          # Общий остаток воды
    total_container_stock: int       # Общий остаток тары (на складах + курьерах)
    containers_at_clients: int       # Тара у клиентов
    stock_on_couriers: int           # Товар на курьерах
    losses_today: int                # Потери за сегодня
    accuracy_rate: float             # Точность учёта (%)
    active_couriers: int             # Курьеров на линии
    pending_shift_closes: int        # Ожидают закрытия смены

class WarehouseBalanceSummary(BaseModel):
    warehouse_id: uuid.UUID
    warehouse_name: str
    balances: list[ProductBalance]   # [{product_id, product_name, type, quantity}]
    total_items: int

class ContainerDistribution(BaseModel):
    at_warehouses: int
    at_couriers: int
    at_clients: int
    lost: int                        # VIRTUAL_LOSS
    total_in_system: int             # |VIRTUAL_VENDOR|
```
