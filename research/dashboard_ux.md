## 1. Резюме для руководителя

### Контекст

MunavvarA (HOD) — платформа полного цикла управления доставкой бутилированной воды на рынке Узбекистана. Система охватывает три основных домена: **заказы и доставка**, **складская логистика** (включая критический учёт возвратной тары) и **финансовый учёт** (двойная бухгалтерия). В системе работают 5 штатных ролей: Администратор, Бухгалтер, Кладовщик, Кассир, Курьер, а также клиенты B2C/B2B.

### Ключевые выводы исследования

1. **Ролевая персонализация — основа эффективности.** Каждая из 5 штатных ролей выполняет принципиально разные задачи. Универсальный дашборд — провал. Необходимо проектировать 5 отдельных «режимов» работы с интерфейсом, где каждый видит только релевантные данные и действия.

2. **Операционный дашборд важнее аналитического.** В бизнесе доставки воды 80% времени пользователей уходит на оперативные задачи (назначение курьеров, подтверждение платежей, отгрузка товара), а не на аналитику. Дашборд должен быть «центром действий», а не «центром отчётов».

3. **Тара — центральный UX-вызов.** Учёт возвратной тары (бутылей) — уникальная особенность бизнеса, не имеющая готовых UX-шаблонов. Необходимо спроектировать интуитивную визуализацию баланса тары на всех уровнях: склад, машина курьера, клиент.

4. **Финансовый реестр требует банковского UX.** Система двойной бухгалтерии с неизменяемым реестром лучше всего визуализируется по паттерну банковской выписки — хронологический список операций с нарастающим итогом.

5. **Закрытие смены — критический wizard-процесс.** Четырёхшаговый процесс (инвентаризация → возврат товара → инкассация → деактивация транспорта) является одним из самых сложных UX-сценариев и требует поэтапного визарда с жёсткой валидацией.

6. **WebSocket для диспетчерской, SSE для остальных.** Реальное время критически важно для диспетчерского экрана (назначение курьеров, статусы заказов). Для остальных модулей достаточно Server-Sent Events или умного поллинга.

7. **Мобильная адаптивность — не «бонус», а необходимость.** Кладовщик работает на планшете на складе, кассир — у кассы, администратор — иногда с телефона. Минимум — tablet-first для складских и кассовых сценариев.

## 2. Ролевые UX-рекомендации

### 2.1 Общие принципы ролевого проектирования

Исследование индустриальных практик (источники: Eleken, Bootstrapdash, DronaHQ, Phenomenon Studio) показывает, что лучшие ролевые админ-панели строятся на трёх принципах:

- **Разные домашние экраны** для каждой роли — после входа каждый видит свой дашборд
- **Контекстная фильтрация навигации** — боковое меню показывает только доступные разделы
- **Ролевые виджеты** — один и тот же экран (например, «Заказы») показывает разные столбцы и действия в зависимости от роли

### 2.2 Администратор (Диспетчер)

**Профиль пользователя:** Самая загруженная роль. Работает полный день за десктопом. Выполняет роль диспетчера, менеджера, и суперпользователя. Высокая частота переключений между разделами.

**Домашний экран — «Центр управления операциями»:**

```
┌──────────────────────────────────────────────────────────────┐
│  СВОДКА ДНЯ                                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ Новые    │ │ В пути   │ │ Доставлено│ │ Выручка  │        │
│  │ заказы   │ │ заказы   │ │ сегодня  │ │ за день  │        │
│  │    12    │ │    5     │ │    28    │ │ 4.2M UZS │        │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
├──────────────────────────────────────────────────────────────┤
│  ТРЕБУЮТ ВНИМАНИЯ (Action Required)                          │
│  ! 3 новых заказа без курьера                                │
│  ! 2 ожидающих подтверждения карточных платежа               │
│  ! 1 курьер не закрыл смену (вчера)                          │
│  ! Низкий остаток: Вода Hayot 19Л (склад Центральный: 15шт) │
├──────────────────────────────────────────────────────────────┤
│  ДИСПЕТЧЕРСКАЯ                                               │
│  [Карта с курьерами] [Список незназначенных заказов]         │
│  [Быстрое назначение: перетащи заказ на курьера]            │
└──────────────────────────────────────────────────────────────┘
```

**Ключевые UX-решения:**

- **Command Palette (Cmd+K)** — быстрый поиск по всей системе: клиенты, заказы, курьеры
- **Быстрые действия** в верхней панели: «+ Новый заказ», «+ Новый клиент», «Закрыть смену»
- **Split-view** для диспетчерской: карта + список заказов, drag-and-drop назначение курьеров
- **Drill-down** из любого числового показателя: клик на «12 новых заказов» открывает отфильтрованный список
- **Keyboard shortcuts** для частых действий: N — новый заказ, A — назначить курьера, F — быстрый поиск

### 2.3 Бухгалтер

**Профиль пользователя:** Работает за десктопом. Основные задачи — подтверждение карточных платежей, просмотр финансовых отчётов, работа со списком должников. Не управляет заказами или складом.

**Домашний экран — «Финансовый центр»:**

```
┌────────────────────────────────────────────────────────────────┐
│  ФИНАНСОВАЯ СВОДКА                                             │
│     ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│     │ Выручка  │ │ В кассе  │ │ Ожидают  │ │ Общий    │        │
│     │ (всего)  │ │ наличные │ │ по карте │ │ долг     │        │
│     │ 45.2M    │ │ 3.1M     │ │ 850K (5) │ │ 12.4M    │        │
│     └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
├────────────────────────────────────────────────────────────────┤
│  ТРЕБУЮТ ДЕЙСТВИЯ                                              │
│  ┌───────────────────────────────────────────────────────┐     │
│  │ Ожидающие подтверждения (5 транзакций)                │     │
│  │ ┌──────┬──────────┬───────────┬──────────┬──────────┐ │     │
│  │ │ Дата │ Клиент   │ Сумма     │ Заказ    │ Действие │ │     │
│  │ │ 01.04│ ООО Арт  │ 200,000   │ #1045  │ [V] [X]  │ │     │
│  │ │ 01.04│ Иванов А.│ 60,000    │ #1042  │ [V] [X]  │ │     │
│  │ └──────┴──────────┴───────────┴──────────┴──────────┘ │     │
│  └───────────────────────────────────────────────────────┘     │
├────────────────────────────────────────────────────────────────┤
│  СВОДКА ПО КУРЬЕРАМ (наличные на руках)                        │
│  Курьер 1: 450,000 | Курьер 2: 320,000 | Курьер 3: 180,000     │
├────────────────────────────────────────────────────────────────┤
│  ТОП ДОЛЖНИКОВ                                                 │
│  1. ООО «Атлас» — 2,500,000 сум (последний платёж: 15.03)      │
│  2. ООО «Глобус» — 1,800,000 сум (последний платёж: 22.03)     │
└────────────────────────────────────────────────────────────────┘
```

**Ключевые UX-решения:**

- **Inline-действия** для подтверждения/отклонения платежей (без перехода на отдельный экран)
- **Модальное окно подтверждения** при отклонении с обязательным полем «Причина»
- **Выписка по счёту** в стиле банковской выписки: хронологический список с нарастающим итогом
- **Фильтры по периоду** с быстрыми пресетами: «Сегодня», «Эта неделя», «Этот месяц», «Произвольный период»
- **Экспорт отчётов** в Excel/PDF одной кнопкой
- **Цветовое кодирование** сумм: красный — задолженность, зелёный — оплачено, жёлтый — ожидает

### 2.4 Кладовщик

**Профиль пользователя:** Работает на планшете/десктопе на складе. Основные задачи — приёмка товара, отгрузка курьерам, инвентаризация. Видит **только свои** склады.

**Домашний экран — «Мой склад»:**

```
┌───────────────────────────────────────────────────────────────┐
│  СКЛАД: Центральный                    [Переключить склад ▼]  │
├───────────────────────────────────────────────────────────────┤
│  ОСТАТКИ ТОВАРОВ                                              │
│  ┌────────────────────────┬────────┬──────────┬────────────┐  │
│  │ Товар                  │ Кол-во │ Мин.уров.│ Статус     │  │
│  │ Вода Hayot 19Л         │ 120    │ 50       │ ✓ Норма    │  │
│  │ Вода MunavvarA 18.9Л   │ 45     │ 50       │ ⚠ Мало     │  │
│  │ Тара Hayot 19Л (пустая)│ 230    │ 100      │ ✓ Норма    │  │
│  │ Тара MunavvarA (пустая)│ 180    │ 100      │ ✓ Норма    │  │
│  └────────────────────────┴────────┴──────────┴────────────┘  │
├───────────────────────────────────────────────────────────────┤
│  БЫСТРЫЕ ДЕЙСТВИЯ                                             │
│  [📦 Загрузить курьера] [📥 Принять возврат] [📋 Инвентари.]│
├───────────────────────────────────────────────────────────────┤
│  ПОСЛЕДНИЕ ОПЕРАЦИИ (сегодня)                                 │
│  09:15 — Загрузка курьера Иванов: Вода Hayot x20, Тара x20    │
│  09:30 — Загрузка курьера Петров: Вода MunavvarA x15          │
│  14:20 — Возврат курьера Иванов: Тара Hayot x5                │
└───────────────────────────────────────────────────────────────┘
```

**Ключевые UX-решения:**

- **Tablet-first дизайн** — крупные кнопки, минимум ввода текста
- **Визуальные индикаторы уровня запаса**: полоса прогресса или светофор (зелёный/жёлтый/красный)
- **Быстрая загрузка курьера**: выбор курьера → таблица товаров со стрелками +/- для установки количества
- **Автоизоляция данных**: кладовщик видит только назначенные ему склады, без возможности выбора чужих
- **Счётчик в инвентаризации**: большие кнопки +/- для ввода фактического количества, автоматический расчёт расхождения
- **Цветовое выделение расхождений**: красная строка — недостача, синяя — излишек, зелёная — совпадает

### 2.5 Кассир

**Профиль пользователя:** Работает на десктопе или планшете на точке продаж. Ключевое требование — **скорость**. POS-интерфейс должен минимизировать количество кликов.

**Домашний экран — «Касса» (POS-режим):**

```
┌──────────────────────────────────────────────────────────────┐
│  КАССА                         Кассир: Алиева С. | Склад: Ц. │
├──────────────────────────────────────────────────────────────┤
│  НОВАЯ ПРОДАЖА                                               │
│  ┌───────────────────────┐  ┌──────────────────────────────┐ │
│  │ КАТАЛОГ               │  │ ЧЕК                          │ │
│  │ ┌─────────┐┌─────────┐│  │                              │ │
│  │ │ Вода    ││ Вода    ││  │ Вода Hayot 19Л     x3  60K   │ │
│  │ │ Hayot   ││MunavvarA││  │ Тара Hayot 19Л     x1  50K   │ │
│  │ │ 19Л     ││ 18.9Л   ││  │                              │ │
│  │ │ 20,000  ││ 22,000  ││  │ ──────────────────────────── │ │
│  │ └─────────┘└─────────┘│  │ ИТОГО:              110,000  │ │
│  │ ┌─────────┐┌─────────┐│  │                              │ │
│  │ │ Тара    ││ Помпа   ││  │ Клиент: [Найти/Walk-in]      │ │
│  │ │ Hayot   ││ мех.    ││  │ Оплата: [Наличные]           │ │
│  │ │ 50,000  ││ 35,000  ││  │                              │ │
│  │ └─────────┘└─────────┘│  │ [ЗАВЕРШИТЬ ПРОДАЖУ]          │ │
│  └───────────────────────┘  └──────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**Ключевые UX-решения (на основе исследований POS UX от Creative Navy, DevPro, Bright Inventions):**

- **Двухколоночный layout**: каталог товаров слева, формируемый чек справа
- **Крупные карточки товаров** с ценой — один клик добавляет в чек
- **Минимум подтверждений** — исследования показывают, что чрезмерные подтверждения в POS раздражают кассиров (Creative Navy)
- **Расстояние до экрана** 80+ см — шрифты не менее 16px, кнопки не менее 44x44 px
- **Быстрый поиск клиента** по телефону с автодополнением
- **Опция «Walk-in»** (анонимный покупатель) одной кнопкой — не заставляет регистрировать клиента
- **Цветовое кодирование** категорий: вода — синий, тара — оранжевый, оборудование — серый
- **Принцип «меньше ввода текста»**: количество через +/- кнопки, не через клавиатуру

### 2.6 Курьер (мобильное приложение)

**Примечание:** Курьер работает через отдельное мобильное приложение, но в контексте админ-панели важно спроектировать **вид администратора на состояние курьеров**.

**Карточка курьера в админ-панели:**

- Текущий статус (на маршруте / свободен / смена не начата)
- Список назначенных заказов с прогрессом
- Баланс наличных на руках
- Остаток товара в машине
- Кнопки: «Назначить заказ», «Закрыть смену», «Создать инкассацию»

## 3. Навигация и информационная архитектура

### 3.1 Принципы информационной архитектуры

По данным GoodData, шесть ключевых принципов для дашбордов:

1. **Структура** — организация данных по логическим группам
2. **Навигация** — предсказуемые пути между разделами
3. **Иерархия** — приоритизация информации по важности
4. **Группировка** — объединение связанных данных
5. **Маркировка** — понятные и однозначные названия
6. **Фильтрация** — возможность сузить видимые данные

### 3.3 Паттерн Drill-Down (Сводка → Деталь → Действие)

Исследования (Pencil & Paper, UXPin, AufaitUX) подтверждают эффективность трёхуровневой модели:

**Уровень 1 — Сводка (Summary):**

- KPI-карточки с числами
- Каждое число — кликабельное
- Отвечает на вопрос «Всё ли в порядке?»

**Уровень 2 — Деталь (Detail):**

- Таблица/список с фильтрами
- Drill-down из KPI: клик на «12 новых заказов» → фильтрованная таблица со статусом «Новый»
- Отвечает на вопрос «Что именно требует внимания?»

**Уровень 3 — Действие (Action):**

- Карточка конкретной сущности (заказ, клиент, транзакция)
- Встроенные действия без перехода: подтвердить, назначить, отклонить
- Отвечает на вопрос «Что мне делать?»

### 3.4 Хлебные крошки

По рекомендациям Smashing Magazine:

- Размещать **под основной навигацией**, над заголовком страницы
- Все элементы — ссылки, **кроме последнего** (текущая страница)
- Обязательны для страниц глубже второго уровня
- На мобильных — показывать только «Назад к [родителю]»

Примеры:

- `Главная > Заказы > Доставки > Заказ #1045`
- `Главная > Клиенты > ООО «Атлас» > Финансы`
- `Главная > Склад > Центральный > Инвентаризация`

### 3.5 Контекстные вкладки

Для сложных карточек (клиент, заказ, курьер) использовать горизонтальные вкладки внутри страницы:

**Карточка клиента:**
`[Профиль] [Заказы] [Финансы] [Тара] [Адреса]`

**Карточка заказа:**
`[Детали] [Позиции] [Финансы] [История статусов]`

**Карточка курьера:**
`[Профиль] [Заказы (сегодня)] [Касса] [Товар в машине] [Смены]`

## 4. UX ключевых рабочих процессов

### 4.1 Диспетчеризация заказов (Order Dispatch)

**Текущий процесс:** Администратор назначает курьеров на новые заказы.

**Рекомендуемый UX-паттерн: Kanban + Drag-and-Drop**

Исследование лучших диспетчерских решений (Onfleet, CXT Software, eLogii) показывает, что наиболее эффективный подход — **split-view с картой и списком**, где:

```
┌──────────────────────┬───────────────────────────────────────┐
│ НЕЗАЗНАЧЕННЫЕ        │                                       │
│ ЗАКАЗЫ               │           КАРТА                       │
│                      │                                       │
│ ┌──────────────────┐ │     [Маркеры заказов на карте]        │
│ │ #1045          │ │     [Маркеры курьеров]                │
│ │ Иванов, ул.Амира │ │                                       │
│ │ Вода x5          │ │     При наведении на курьера —        │
│ │ [Назначить ▼]    │ │     показать его маршрут              │
│ └──────────────────┘ │                                       │
│ ┌──────────────────┐ │     При наведении на заказ —          │
│ │ #1046          │ │     показать ближайших курьеров       │
│ │ ООО Глобус       │ │                                       │
│ │ Вода x20, Тара x5│ │                                       │
│ │ [Назначить ▼]    │ │                                       │
│ └──────────────────┘ │                                       │
│                      │                                       │
│ КУРЬЕРЫ              │                                       │
│ ┌──────────────────┐ │                                       │
│ │ Петров (3/8)     │ │                                       │
│ │ Сидоров (5/8)    │ │                                       │
│ │ Алиев (2/8)      │ │                                       │
│ └──────────────────┘ │                                       │
└──────────────────────┴───────────────────────────────────────┘
```

**Ключевые решения:**

- **Drag-and-drop** назначения: перетаскивание заказа на курьера
- **Автоматическое предложение** курьера на основе географической близости и текущей загрузки
- **Индикатор загрузки курьера**: «3/8 заказов» с прогресс-баром
- **Групповое назначение** (batch): выделить несколько заказов → назначить одному курьеру
- **Статусная лента** (Kanban): Новый → Назначен → В пути → Прибыл → Доставлен
- **Фильтр по зонам доставки**: быстрый выбор района города

### 4.2 Закрытие смены курьера

**Это самый сложный UX-процесс в системе.** Четыре шага выполняются атомарно.

**Рекомендуемый паттерн: Wizard/Stepper (4 шага)**

Исследования (Eleken, Clarity Design, PatternFly) показывают, что wizard оптимален для:

- Задач с 3-7 шагами
- Процессов с жёсткой последовательностью
- Ситуаций, где каждый шаг требует валидации перед переходом к следующему

```
    [1. Инвентаризация]  →  [2. Возврат товара]  →  [3. Инкассация]  →  [4. Завершение]
         ●                        ○                       ○                    ○
```

**Шаг 1: Инвентаризация**

```
┌──────────────────────────────────────────────────────────────┐
│  ЗАКРЫТИЕ СМЕНЫ — Шаг 1 из 4: Инвентаризация                 │
│  Курьер: Петров И.А. | Машина: 01A777DA                      │
├──────────────────────────────────────────────────────────────┤
│  Укажите фактическое количество товара в машине:             │
│                                                              │
│  ┌──────────────────┬──────────┬──────────┬──────────────┐   │
│  │ Товар            │ По учёту │ Факт     │ Расхождение  │   │
│  │ Вода Hayot 19Л   │    5     │ [-][5][+]│ ✓ Совпадает  │   │
│  │ Вода MunavvarA   │    3     │ [-][2][+]│ ✗ -1 (недост)│   │
│  │ Тара Hayot (пуст)│   12     │ [-][12][+]│ ✓ Совпадает │   │
│  │ Тара MunavvarA   │    8     │ [-][9][+]│ ✗ +1 (излиш) │   │
│  └──────────────────┴──────────┴──────────┴──────────────┘   │
│                                                              │
│  ⚠ Обнаружены расхождения по 2 позициям.                    │
│    Необходимо оформить акт списания/находки перед            │
│    продолжением.                                             │
│                                                              │
│  [Оформить акт списания]  [Оформить акт находки]             │
│                                                              │
│  [← Назад]                                    [Далее →]      │
│                                   (кнопка неактивна пока     │
│                                    есть расхождения)         │
└──────────────────────────────────────────────────────────────┘
```

**Шаг 2: Возврат товара на склад**

- Показать все позиции, которые курьер возвращает
- Автоматически подставить весь остаток
- Выбрать склад для возврата (dropdown)
- Большая кнопка подтверждения

**Шаг 3: Инкассация**

- Показать баланс наличных на руках у курьера
- Ввести сумму инкассации (по умолчанию = весь баланс)
- Выбрать счёт зачисления (по умолчанию = Касса)
- Подтверждение с повторением суммы

**Шаг 4: Завершение**

- Summary всех операций: что вернули, сколько сдали
- Большая зелёная кнопка «Закрыть смену»
- После закрытия — неизменяемый отчёт по смене

**Критически важные UX-решения:**

- Кнопка «Далее» **неактивна** при наличии расхождений (Шаг 1)
- Кнопка «Назад» **всегда доступна** для исправления
- **Автосохранение** промежуточных данных — если вкладка закрылась, данные не пропадут
- **Финальное подтверждение** — модальное окно с полным summary и кнопкой «Подтвердить закрытие смены»
- **Цветовая индикация** расхождений: красный — недостача, синий — излишек

### 4.3 Верификация платежей по карте

**Процесс:** Бухгалтер проверяет и подтверждает/отклоняет карточные платежи.

**Рекомендуемый UX-паттерн: Inline Actions в таблице**

```
┌─────────────────────────────────────────────────────────────────────────┐
│  ОЖИДАЮЩИЕ ПОДТВЕРЖДЕНИЯ                                    Всего: 5    │
├─────────────────────────────────────────────────────────────────────────┤
│  ┌─────┬──────────┬────────────┬──────────┬─────────┬───────────────┐   │
│  │  #  │ Дата     │ Клиент     │ Сумма    │ Заказ   │ Действие      │   │
│  ├─────┼──────────┼────────────┼──────────┼─────────┼───────────────┤   │
│  │  1  │ 01.04    │ ООО Арт    │ 200,000  │ #1045 │   [✓] [✗]    │   │
│  │  2  │ 01.04    │ Иванов А.  │ 60,000   │ #1042 │   [✓] [✗]    │   │
│  │  3  │ 31.03    │ ООО Глобус │ 440,000  │ #1038 │   [✓] [✗]    │   │
│  │  4  │ 31.03    │ Петрова Н. │ 40,000   │ #1035 │   [✓] [✗]    │   │
│  │  5  │ 30.03    │ ООО Альфа  │ 110,000  │ #1030 │   [✓] [✗]    │   │
│  └─────┴──────────┴────────────┴──────────┴─────────┴───────────────┘   │
│                                                                         │
│  Batch: [Выбрать все] → [Подтвердить выбранные]                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Ключевые решения:**

- **Inline-кнопки** подтверждения/отклонения — минимум кликов
- **Batch-подтверждение**: выбрать несколько → подтвердить все разом
- При **отклонении** — обязательное модальное окно с текстовым полем «Причина»
- При **подтверждении** — лёгкий confirmation toast: «Платёж #1045 подтверждён» с кнопкой «Отменить» (5 секунд)
- **Подсветка «старых» платежей**: если ожидает > 24 часов — оранжевый фон, > 48 часов — красный
- **Сортировка по умолчанию**: самые старые сверху (FIFO)

### 4.4 Онбординг клиента (Единое окно)

**Процесс:** Администратор за один шаг создаёт клиента + адрес + тару + первый заказ.

**Рекомендуемый UX-паттерн: Multi-step Wizard (4 шага)**

```
    [1. Клиент]  →  [2. Адрес доставки]  →  [3. Тара]  →  [4. Первый заказ]
        ●                   ○                    ○               ○
```

**Шаг 1 — Данные клиента:**

- Имя, Телефон (+998 маска), Тип (B2C/B2B toggle)
- Проверка дублей по телефону в реальном времени
- Если клиент найден — предложить «Открыть существующего»

**Шаг 2 — Адрес доставки:**

- Текстовое поле с адресом
- Ориентир (необязательно)
- Контактное лицо (если B2B)

**Шаг 3 — Начальная тара:**

- Список типов бутылей с полями количества
- Пояснение: «Укажите количество пустых бутылей, уже имеющихся у клиента»
- Можно пропустить (по умолчанию 0)

**Шаг 4 — Первый заказ (необязательный):**

- Список товаров с количеством
- Автоматическая проверка правила обмена тары
- Можно пропустить — только создать клиента

**Ключевые решения:**

- **Шаги 3 и 4 — опциональные** (возможность пропустить)
- **Inline-валидация** номера телефона (формат +998XXXXXXXXX)
- **Проверка дублей** в реальном времени при вводе телефона
- **Видимый progress indicator** наверху
- **Review-экран** перед финальным подтверждением: «Будет создано: клиент, адрес, тара 5 шт., заказ на 10 бутылей»
- **Атомарность** — на бэкенде всё создаётся в одной транзакции

### 4.5 Продажа со склада (POS-процесс кассира)

**Рекомендуемый UX-паттерн: Single-Screen POS**

На основе исследований Creative Navy (16 UX-факторов POS) и DevPro (10 тактик):

**Принципы POS для MunavvarA:**

1. **Минимум шагов** — от открытия чека до завершения продажи не более 4 кликов
2. **Крупные элементы** — кнопки товаров минимум 44x44px, шрифт минимум 16px
3. **Визуальная группировка** товаров по категориям (вода, тара, оборудование)
4. **Автоматическая тарная логика** — при добавлении воды система автоматически показывает предупреждение о необходимости тары
5. **Walk-in по умолчанию** — кассиру не нужно каждый раз выбирать «анонимный покупатель», это дефолт
6. **Быстрый поиск клиента** — ввод номера телефона, список совпадений
7. **Один способ оплаты** для самовывоза — наличные (не показывать лишние опции)
8. **Печать чека** — кнопка после завершения продажи (не модальное окно)
9. **История сегодняшних продаж** — доступна в один клик, не перекрывая POS

### 4.6 Карточка клиента (360-degree view)

Исследования CRM-дизайна (CareCloud, UI Bakery, Velaris, Monday.com) показывают, что лучшие карточки клиента строятся по принципу **единого источника правды** — вся информация о клиенте на одном экране с вкладками.

## 5. Стратегия уведомлений и оповещений

### 5.1 Классификация уведомлений

На основе исследований (Smashing Magazine, Toptal, SetProduct, NNGroup):

**Высокий приоритет (красный badge, звуковой сигнал):**

- Новый заказ без назначенного курьера (> 15 мин)
- Курьер не закрыл вчерашнюю смену
- Критический остаток товара на складе (ниже минимума)
- Ошибка в финансовой проводке

**Средний приоритет (оранжевый badge):**

- Ожидающие подтверждения карточные платежи (> 2 часов)
- Клиенты с задолженностью > 30 дней
- Курьер на маршруте > 2 часов без обновления статуса

**Низкий приоритет (серый badge):**

- Новая регистрация клиента
- Выполненная доставка
- Закрытая смена курьера
- Системные уведомления

### 5.2 Паттерн уведомлений

**Рекомендуемая реализация:**

```
┌──────────────────────────────────────────────────────────────┐
│  [🔔 3]  ← Badge с числом непрочитанных в header            │
│                                                              │
│  При клике — dropdown-панель:                                │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ СЕГОДНЯ                                              │    │
│  │ ● 3 заказа ожидают назначения          15 мин назад  │    │
│  │ ● Ожидание подтверждения: 850,000 UZS  1 час назад   │    │
│  │                                                      │    │
│  │ ВЧЕРА                                                │    │
│  │ ○ Курьер Петров закрыл смену           вчера, 19:30  │    │
│  │ ○ Новый клиент: Иванов А.А.            вчера, 14:20  │    │
│  │                                                      │    │
│  │ [Показать все уведомления]                           │    │

```

### 5.3 Уведомления по ролям

| Событие                  | Админ   | Бухгалтер | Кладовщик | Кассир  |
| ------------------------ | ------- | --------- | --------- | ------- |
| Новый заказ              | Высокий | --        | --        | --      |
| Ожидает платёж по карте  | Средний | Высокий   | --        | --      |
| Низкий остаток           | Высокий | --        | Высокий   | Средний |
| Незакрытая смена         | Высокий | Средний   | --        | --      |
| Клиент-должник > 30 дней | Средний | Средний   | --        | --      |
| Новый клиент             | Низкий  | --        | --        | --      |
| Доставка завершена       | Низкий  | --        | --        | --      |

### 5.4 Принципы управления уведомлениями

По рекомендациям Smashing Magazine:

- **Начинать с малого**: лучше меньше уведомлений высокого качества, чем много бесполезных
- **Группировка однотипных**: «3 заказа ожидают назначения» вместо трёх отдельных
- **Пользовательский контроль**: страница настроек, где можно включить/выключить категории
- **Quiet hours**: возможность отключить уведомления на время
- **Деградация канала**: если уведомлений слишком много — предложить перейти на дайджест (ежедневная сводка)

### 5.5 Блок «Требуют внимания» на дашборде

Помимо dropdown-уведомлений, на домашнем экране каждой роли должен быть **статический блок** с action-required элементами:

- Это **не уведомления**, а **задачи** — они не исчезают, пока не будут выполнены
- Каждый элемент — кликабельная ссылка, ведущая к действию
- Счётчик обновляется в реальном времени
- Визуально отличается от остального контента (другой фон, иконка !)

## 6. Поиск и фильтрация

### 6.1 Глобальный поиск (Command Palette)

**Паттерн: Cmd+K / Ctrl+K**

Исследования (Knock, NNGroup) показывают, что command palette — наиболее эффективный инструмент навигации для опытных пользователей:

```
┌──────────────────────────────────────────────────────────────┐
│  🔍 Поиск...                                      [Ctrl+K]  │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ Введите имя клиента, номер заказа, или телефон...    │    │
│  │                                                      │    │
│  │ НЕДАВНИЕ                                             │    │
```

### 6.2 Фильтрация в таблицах

На основе исследований (Pencil & Paper, Eleken, LogRocket, AufaitUX):

**Стратегия фильтрации для таблицы заказов:**

```
┌──────────────────────────────────────────────────────────────┐
│  ЗАКАЗЫ                                                      │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ Статус: [Все ▼] Период: [Сегодня ▼] Курьер: [Все ▼]  │    │
│  │ Тип: [Все ▼]    Оплата: [Все ▼]                      │    │
│  │                                                      │    │
│  │ Применённые фильтры:                                 │    │
│  │ [Статус: Новый ✕] [Период: Сегодня ✕] [Очистить все]│    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  Найдено: 12 заказов                                         │
│  ┌─────┬──────┬──────────┬──────────┬─────────┬──────────┐   │
│  │  #  │Статус│ Клиент   │ Сумма    │ Курьер  │ Действие │   │
│  │ ... │ ...  │ ...      │ ...      │ ...     │ ...      │   │
│  └─────┴──────┴──────────┴──────────┴─────────┴──────────┘   │
└──────────────────────────────────────────────────────────────┘
```

**Принципы фильтрации:**

1. **Видимые фильтры по умолчанию** — самые используемые (статус, дата) видны сразу, остальные в «Ещё фильтры»
2. **Lozenges/Pills** — примённые фильтры отображаются как удаляемые «таблетки» над таблицей
3. **Кнопка Apply** — для тяжёлых таблиц (>1000 записей) фильтрация по кнопке, не в реальном времени
4. **Live-фильтрация** — для лёгких таблиц (<300ms ответ сервера) обновление при выборе
5. **Счётчик результатов** — всегда показывать «Найдено: N записей»
6. **Сохранение фильтров** — возможность сохранить набор фильтров как «Мой вид»
7. **Фильтрация по столбцам** — клик на заголовок таблицы для сортировки, иконка фильтра для фильтрации
8. **Поиск внутри фильтра** — для dropdown с >20 опций (например, список клиентов)

### 6.3 Фильтрация для разных сущностей

| Сущность          | Основные фильтры                             | Дополнительные фильтры                             |
| ----------------- | -------------------------------------------- | -------------------------------------------------- |
| Заказы            | Статус, Дата, Тип (доставка/самовывоз)       | Курьер, Клиент, Способ оплаты, Сумма от/до         |
| Клиенты           | Тип (B2C/B2B), Статус (активен/заблокирован) | Баланс от/до, Дата последнего заказа, Район        |

| Складские остатки | Склад, Категория товара                      | Мин./макс. количество, Статус (норма/мало/критич.) |
| Перемещения       | Тип перемещения, Период                      | Склад-отправитель, Склад-получатель, Товар         |

## 7. Стратегия мобильной адаптивности

### 7.1 Анализ мобильных сценариев

| Роль          | Основное устройство | Мобильные сценарии                                     |
| ------------- | ------------------- | ------------------------------------------------------ |
| Администратор | Десктоп             | Срочный просмотр заказов, назначение курьера «на ходу» |
| Бухгалтер     | Десктоп             | Подтверждение платежей, просмотр отчётов с телефона    |
| Кладовщик     | Планшет (!)         | Основная работа: приёмка, отгрузка, инвентаризация     |
| Кассир        | Десктоп/Планшет     | POS-интерфейс на стационарном устройстве               |
| Курьер        | Мобильный (!)       | Полная работа через мобильное приложение               |

### 7.2 Стратегия адаптивности по приоритетам

**Приоритет 1 — Desktop-first (Администратор, Бухгалтер):**

- Основной рабочий инструмент — десктоп
- Мобильная версия — read-only + критические действия (назначение курьера, подтверждение платежа)
- Упрощённый sidebar → hamburger menu
- Таблицы → карточный вид
- Графики → упрощённые числа

**Приоритет 2 — Tablet-first (Кладовщик):**

- Дизайн оптимизирован для 10-12" планшетов
- Крупные тач-элементы (минимум 44x44px по рекомендациям Apple/Google)
- Grid-layout для товаров (как в каталоге)
- Инвентаризация — большие кнопки +/- вместо клавиатурного ввода
- Landscape-ориентация по умолчанию для таблиц

**Приоритет 3 — Responsive Web (Кассир):**

- Фиксированный layout для POS (не адаптивный — работает на конкретном устройстве)
- Touch-оптимизированный для планшетных касс
- **Не оптимизировать для мобильных** — кассовый аппарат не бывает на телефоне

### 7.3 Паттерны мобильной адаптации

По исследованиям (AufaitUX, UXPin, AdminUIUX):

**Навигация:**

- Десктоп: фиксированный сайдбар 240px
- Планшет: сворачиваемый сайдбар (иконки, раскрывается по hover/tap)
- Мобильный: hamburger menu (верхний левый угол)

**Таблицы:**

- Десктоп: полная таблица со всеми столбцами
- Планшет: скрыть 2-3 наименее важных столбца
- Мобильный: карточный вид (каждая строка → карточка)

**Фильтры:**

- Десктоп: горизонтальная панель фильтров над таблицей
- Планшет: сворачиваемая панель фильтров
- Мобильный: sheet (выдвижная панель снизу) с фильтрами

**Действия:**

- Десктоп: inline-кнопки в строке таблицы
- Планшет: inline-кнопки (крупнее)
- Мобильный: swipe-действия или контекстное меню по long-press

## 8. Стратегия обновлений в реальном времени

### 8.1 Выбор технологии

На основе исследований (Dev.to, GetStream, OpenReplay, Medium):

| Сценарий                                          | Технология                   | Обоснование                                        |
| ------------------------------------------------- | ---------------------------- | -------------------------------------------------- |
| Диспетчерская (статусы заказов, позиции курьеров) | **WebSocket**                | Двусторонняя связь, высокая частота обновлений     |
| Уведомления                                       | **SSE (Server-Sent Events)** | Односторонняя передача, проще в реализации         |
| Финансовые данные (дашборд, балансы)              | **Умный поллинг** (30 сек)   | Не критично по скорости, проще поддерживать        |
| Складские остатки                                 | **SSE**                      | Обновления по событию (перемещение), не по таймеру |

### 8.2 Оптимистичные обновления

По исследованиям (RxDB, LevelUp Coding):

**Где применять:**

- Назначение курьера на заказ → сразу показать «Назначен», подтвердить с сервера
- Подтверждение платежа → сразу убрать из списка ожидающих
- Добавление товара в чек (POS) → сразу обновить итого

**Где НЕ применять:**

- Закрытие смены — слишком критическая операция, показывать спиннер
- Финансовые проводки — ждать ответа сервера
- Удаление/блокировка — ждать подтверждения

### 8.3 UX-паттерны для обновлений

**Toast-уведомление о получении обновления:**

```
┌─────────────────────────────────────┐
│ 🔄 Заказ #1047 перешёл в "В пути"  │
│    [Посмотреть]         [Закрыть]   │
└─────────────────────────────────────┘
```

**Индикатор свежести данных:**

```
Последнее обновление: 5 сек назад  ●  (зелёный = свежие данные)
Последнее обновление: 2 мин назад  ●  (жёлтый = слегка устарело)
Последнее обновление: > 5 мин      ●  (красный = потеря соединения)
```

**Стратегия переподключения:**

- При потере WebSocket — показать banner: «Потеряно соединение. Переподключение...»
- Exponential backoff с jitter для переподключения
- При восстановлении — автоматический запрос пропущенных обновлений
- Кнопка «Обновить данные» всегда доступна для ручного обновления

## 10. Доступность (Accessibility)

### 10.1 Стандарты и требования

На основе WCAG 2.1 AA и рекомендаций W3C, GoodData, Tableau:

**Базовые требования для MunavvarA:**

1. **Контраст** — минимум 4.5:1 для текста, 3:1 для крупного текста и UI-элементов
2. **Клавиатурная навигация** — все функции доступны с клавиатуры (Tab, Enter, Escape, Arrow keys)
3. **Focus indicators** — видимый индикатор фокуса на всех интерактивных элементах
4. **Screen reader support** — ARIA-атрибуты для динамического контента (уведомления, обновления таблиц)
5. **Альтернативный текст** — для всех иконок и визуальных индикаторов

### 10.2 Специфические рекомендации

**Цветовое кодирование:**

- **Никогда** не использовать только цвет для передачи информации
- Добавлять иконки/текст: ✓ Норма | ⚠ Мало | ✗ Критично (вместо зелёный/жёлтый/красный)
- Паттернированные заливки для графиков (помимо цвета)

**Таблицы:**

- Заголовки столбцов с `scope="col"` для screen readers
- Строки с кликабельными действиями — `role="row"` и `aria-label`
- Пагинация доступна с клавиатуры

**Формы:**

- Каждое поле ввода имеет видимый label (не только placeholder)
- Сообщения об ошибках связаны с полями через `aria-describedby`
- Обязательные поля обозначены текстом «(обязательно)» помимо звёздочки \*

**Модальные окна:**

- Фокус автоматически переносится в модальное окно при открытии
- `Escape` закрывает модальное окно
- Фокус возвращается на элемент, открывший модальное окно, после закрытия
- `aria-modal="true"` для блокировки фонового контента

**Уведомления:**

- `aria-live="polite"` для обычных уведомлений
- `aria-live="assertive"` для критических оповещений
- Текстовое описание для звуковых сигналов

### 10.3 Отображение данных «Показать как таблицу»

Для графиков и визуализаций — предоставить альтернативный табличный вид:

- Кнопка «Показать как таблицу» рядом с каждым графиком
- Таблица содержит те же данные, что и график, но в текстовом формате
- Screen reader автоматически получает табличное представление

## 12. Практические рекомендации

### 12.1 Приоритизация разработки (фазы)

**Фаза 1 — MVP админ-панели (4-6 недель):**

- Ролевая навигация (sidebar с фильтрацией по роли)
- Дашборд администратора (KPI-карточки + блок «Требуют внимания»)
- Управление заказами (CRUD + таблица с фильтрами + назначение курьера)
- Управление клиентами (CRUD + карточка клиента с вкладками)
- Базовый POS для кассира (каталог + чек)

**Фаза 2 — Финансы и склад (3-4 недели):**

- Финансовый дашборд бухгалтера
- Подтверждение карточных платежей (inline actions)
- Складской дашборд кладовщика
- Загрузка/выгрузка курьера
- Выписка по счёту (банковский стиль)

**Фаза 3 — Продвинутые workflows (3-4 недели):**

- Wizard закрытия смены
- Wizard онбординга клиента (Единое окно)
- Диспетчерская с картой (split-view)
- Batch-операции (массовое назначение, массовое подтверждение)
- Уведомления в реальном времени (SSE/WebSocket)

**Фаза 4 — Оптимизация и power-user features (2-3 недели):**

- Command Palette (Ctrl+K)
- Клавиатурные сокращения
- Сохранённые фильтры
- Экспорт отчётов
- Персонализация дашборда (переставляемые виджеты)

| Время до первого действия      | < 5 сек          | От загрузки дашборда до первого клика        |

### 12.4 Антипаттерны — чего избегать

1. **Универсальный дашборд для всех ролей** — каждый будет видеть 80% ненужной информации
2. **Модальные окна для каждого действия** — особенно критично для POS и диспетчерской
3. **Полная загрузка всех данных** — использовать пагинацию, lazy loading, виртуализацию
4. **Чрезмерные подтверждения** — подтверждения только для деструктивных и финансовых действий
5. **Скрытие ошибок** — всегда показывать inline-ошибки рядом с полями
6. **Auto-refresh без контроля** — пользователь должен знать, когда данные обновились
7. **Отсутствие feedback** — каждое действие должно иметь видимый результат (toast, обновление строки, анимация)
8. **Фиксированные формы без прогрессивного раскрытия** — длинные формы разбивать на секции или шаги
9. **Отсутствие Undo** — для некритических действий предлагать отмену (5-секундный toast)
10. **Игнорирование мобильных сценариев кладовщика** — планшет на складе — основное рабочее устройство

### 12.5 Паттерн подтверждения критических действий

На основе исследований (NNGroup, UX Planet, UX Movement):

**Уровни подтверждения по критичности:**

| Уровень            | Действие                 | Паттерн                                | Пример                              |
| ------------------ | ------------------------ | -------------------------------------- | ----------------------------------- |
| Лёгкий             | Редактирование           | Без подтверждения, undo-toast          | Изменение статуса заказа            |
| Средний            | Отмена, отклонение       | Modal с объяснением последствий        | Отмена заказа                       |
| Тяжёлый            | Финансовые операции      | Modal + ввод суммы/причины             | Инкассация, ручная проводка         |
| Критический        | Закрытие смены, доставка | Modal + summary + «Подтвердить» кнопка | Завершение доставки                 |
| Экстра-критический | Удаление данных          | Modal + ввод текста подтверждения      | Удаление товара, блокировка клиента |

**Правила дизайна диалогов подтверждения:**

- Конкретно описывать последствия: «Заказ #1045 будет отменён. Клиенту будет возвращена тара.»
- Фокус по умолчанию — на безопасном действии (Cancel), **не** на деструктивном
- Деструктивная кнопка — красного цвета
- Текст кнопок — конкретные глаголы: «Отменить заказ», «Подтвердить платёж» (не «ОК»/«Да»)
- Не злоупотреблять — если подтверждения появляются слишком часто, пользователи их игнорируют

### 12.6 Batch-операции для админ-панели

На основе исследований (Eleken, SaaS Interface, Jira UX):

**Сценарии batch-операций в MunavvarA:**

| Операция                        | Где              | Как                                             |
| ------------------------------- | ---------------- | ----------------------------------------------- |
| Массовое назначение курьера     | Список заказов   | Checkbox выбор → dropdown курьера → «Назначить» |
| Массовое подтверждение платежей | Список ожидающих | Checkbox → «Подтвердить выбранные»              |
| Массовый экспорт                | Любая таблица    | Checkbox → «Экспорт в Excel»                    |
| Массовая архивация товаров      | Каталог          | Checkbox → «Архивировать выбранные»             |

**UX-паттерн batch-действий:**

```
┌──────────────────────────────────────────────────────────────┐
│  При выборе 1+ строк появляется floating action bar:         │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ Выбрано: 5 заказов  [Назначить курьера]  [Отменить]  │    │
│  │                     [Экспорт]           [Снять выбор]│    │
│  └──────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

- Floating bar появляется при выборе первого элемента
- Прилипает к низу экрана при прокрутке
- Показывает количество выбранных элементов
- Действия адаптируются — если не все выбранные допускают действие, кнопка неактивна с tooltip объяснения
